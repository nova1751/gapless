# 原生跳转后整首缓存补齐实验

Windows 网易云 3.1.43.205627，2026-11-15。生产安装仍为 0.4.5。用户新增要求：跳转优先出声，播放时后台补齐整首，使用原生磁盘缓存及清理。

## 原生默认对照

关闭插件，在此前未完整缓存的一首 250.270 秒、51532448 字节无损歌曲上正常起播，约 9 秒时原生 Seek 到 215.270 秒。随后暂停并观察，再使用 app.exit 正常退出。原生索引为：

```json
{"size":"51532448","t":true,"zone":["0 9497599","44492351 51532447"]}
```

文件长度等于整曲，但中间 34994751 字节仍是缺口。本次观察不能证明所有版本和长时间等待都不会补齐，但足以否定“跳转后已经保证整首缓存”。本轮最初为打开调试端口使用过进程重启；上述数据来自之后新曲实验及正常退出，不以强制结束来判断索引刷新。

## 不持续播放的原生补齐

重启后不发送原生 Play，通过当前授权源建立独立实验 playId，Load → Seek 65 秒 → 等待取数 → Stop。Stop 后无需退出应用，索引更新为：

```json
{"size":"51532448","t":true,"zone":["0 28520843","44492351 51532447"]}
```

第二轮 Load → Seek 140 秒 → 等待取数 → Stop 后：

```json
{"size":"51532448","t":true,"zone":["0 51532447"]}
```

最终 storage.queryNewCacheTrack 返回 cached=100。读取整首 .uc，经已有 XOR 还原后计算 MD5，与授权源标识一致。此阶段原生 Play 命令计数 0，Stop 2；原生 playedTime=0.221、playedAudioTime=0.266，没有持续增加。初始非零值尚未解释，不据此声称没有任何解码/统计开销。

所有歌曲文件和索引由原生写入；插件未自行落盘，也未用第二次整曲网络下载完成校验。本次未删除用户缓存、未修改原生下载策略。成功证明可以请求原生补齐并登记完整缓存，尚未证明与正在运行的 Web 音乐并发时没有影响。

## 实施增量

新增 `windows/cache-coverage.js`：严格解析原生有效区间、转换包含末尾的索引到半开区间、合并范围、求缺口、利用已验证 FLAC 帧索引找缺口之前的 Seek 位置。不能用 t=true 或文件长度当成完整缓存。此模块尚未加入发布包，先作为原生数据源原型的基础。

检查：Node 单文件语法通过；使用实际部分索引核对缺口；临时检查覆盖相邻区间合并、错误长度和越界拒绝，没有添加常驻测试。

下一步必须实现独占原生实例的可取消调度、当前播放/Seek 抢占、补齐任务背压、原生辅助事件隔离、Stop 后索引刷新等待和源身份核对。还需复核固定初始计时、完整缓存重启复用、清缓存和实际声音。不能把本次试验直接打包成已对齐的正式版本。
