# 跨平台无缝播放最佳实践与实施方案

最新保真修正见 [Mac 0.3.4 / Windows 0.4.6](AUDIO_FIDELITY_0.3.4.md)：共享转换保留原整数 PCM；开启原生淡入淡出、杜比或已识别音效时走原生。保持用户设置，不暗中忽略音效或降档。下面 0.3.3 矩阵保留该轮证据，不能当作本版全部验收。

最新对齐见 [Windows 0.4.6 / Mac 0.3.3 矩阵](PLATFORM_ALIGNMENT_0.4.6_0.3.3.md)：Mac 已安装，补上本地 FLAC 和切歌后后台补缓存；Windows 原生数据源、后台补齐和本地播放已有实机记录，最新 0.4.6 改动尚未复测。默认 Windows 打包采用原生数据源。历史版本表格和早期只读缓存限制不代表最新实现。

最新 Mac 0.3.1 已接入共用增量解码、Range 和 PCM 分块路径；Mac 原生取数/提交有效区间已验证并安装，见 [实机记录](MAC_NATIVE_CACHE_0.3.1.md)。具体以 [Mac 当前说明](../mac/README.md) 为准。下文 Mac 0.2.5 表格为历史基线。

当前原生缓存候选的实现、安装与验收情况见 [统一状态表](CURRENT_STATUS.md)；以下默认包和历史平台记录不代表该候选的全部能力。

后续路线决策以[原生行为对齐调研方案](GAPLESS_NATIVE_PARITY_PLAN.md)为准：保留原生数据与缓存所有权，分别验证原生连续输出和 Web 连续输出；其中原生取数＋Web 连续输出已分别进入 Windows 与 Mac 候选；纯原生连续输出仍没有可靠接入入口。下文仍记录各版本已实施内容及历史约束。

当前 Windows 0.4.5 增加原生清理入口联动和已知原生预加载通道隔离，见 [0.4.5 验证及边界](WINDOWS_CACHE_LIFECYCLE_0.4.5.md)。Windows 0.4.4 已加入带源身份的 64 MiB 共享编码区块缓存、请求去重和按需预读，见 [0.4.4 实施与边界](WINDOWS_SHARED_CACHE_0.4.4.md)。原生写回和 PCM 分块淘汰尚未实现。Windows 0.4.3 增加带索引 FLAC 的按区块跳转，避免从头等待解码，见 [0.4.3 实施与验证](WINDOWS_INDEXED_SEEK_0.4.3.md)。0.4.2 已增加 Seek 缓冲检查和热切歌资源复用；手动选曲的宿主停止至新音源交付间隔仍存在，见 [0.4.2 验证与限制](WINDOWS_STREAMING_0.4.2.md)。基础流式方案从 Windows 0.4.0 引入：受支持 FLAC 首段解码后起播，同钟连续输出；下一首不再要求已听过或完整磁盘缓存。完整 MD5 改为读取结束时验证，失败回退。详见 [0.4.0 方案和验证](WINDOWS_STREAMING_0.4.0.md)。Mac 0.3.1 已单独接入流式及原生数据源；以下生命周期/矩阵保留 Windows 0.3.0 / macOS 0.2.5 的历史基线，不能当作 Windows 当前入口与完整性策略。

## 目标与约束

只提供无缝播放及一个开关。Windows 入口只在主界面右上角，不注入歌词详情页；Mac 复用宿主原菜单。网易云负责账号、授权、音质、音量、队列和音效偏好。未知协议、试听、特殊格式或无法保留的设置回到原生；不通过降档、交叉淡化、静音裁剪或 DSP 制造“无缝”。

“使用相同核心”不等于两端功能、耗时或设备输出完全一致。平台桥、缓存文件格式、输入授权和系统媒体控制须分别验收。

以下通用顺序中的“完整磁盘缓存/网络读取”是旧 Web 数据源路径；当前受支持的两端原生数据源优先读同源内存及 IDX 有效区间，缺口交原生准备。Mac 0.3.3 已采用与 Windows 同类的有界后台补齐策略。清缓存屏障仍有实现差异：Windows 观察停止后索引/元数据稳定，Mac 停止辅助任务后固定等待 500 毫秒；均不是原生原子 flush 的证明。

## 推荐生命周期

1. 启动时安装桥拦截，读取持久化开关。初始化请求队列有明确的数量/时间上限；未知配置不启动 Web 声音，配置读取失败或初始化超时回到原生。
2. 得到当前有效的网易云授权资料后准备恢复曲目：先复用匹配的解码内存，再读同档位完整磁盘缓存，否则读取同一授权网络源。准备阶段不伪造原生 Load 完成，不自动播放。
3. 解码使用独立 OfflineAudioContext，输出 AudioContext 根据真实源采样率创建；资源任务不能更改正在播放的时钟。不要在启动时先固定 44.1kHz。
4. 当前曲准备好后预取可信下一首，包括暂停状态。授权/队列不确定时不猜测。预取不创建播放节点，不改变暂停意图。
5. 自动跨曲用同一音频时钟提前预约下一首 start(when)，不能依赖 JS End 回调再开声。40ms 状态轮询不是40ms接缝精度。
6. 手动换歌取消旧节点/预约，保留可复用的匹配缓冲与同采样率输出。不同采样率按策略重建，不能声称所有混合规格都零间隔。
7. 关闭时取消预取/预约、停止可视化和 Web 输出，恢复同曲、位置、音量及最新暂停/播放意图。状态显示覆盖整个恢复事务。闲置、账号/档位变化和内存压力及时释放资源。

## 缓存与内存

- 优先级：匹配的已解码内存 → 已授权本地文件/完整原生磁盘缓存 → 同一授权网络源。
- 文件名或曲名相同不代表同一音源。核对曲目、档位、长度、MD5/源身份、权限；完整校验后才供音乐输出。
- 插件对原生文件仍是只读；受支持的原生数据源由网易云 Load/Seek/Stop 写盘，重启复用须核对提交索引。旧 Web 网络路径不会自动写回原生缓存，不能用“已经播过”代替命中证据。
- Windows 保留当前、可信下一首，以及最多一首最近播放缓冲。最近一首上限128MiB，全部受共享512MiB预算约束；内存不足优先释放可选历史缓冲，关闭后全部释放。
- 不建立第二套永久音乐库，不扫描整个磁盘，不写入未知 UC/索引格式，不绕过权限，也不让原生和 Web 各下载同一首来制造命中。

### 原生缓存写回的后续实施门槛

本轮查看的 Windows Storage 接口提供 getTrackFromCacheFast、setPlayCacheConfig、查询和扫描下载等能力，没有确认一个接受已下载字节、并原子提交播放缓存的公开接口。方法名存在也不能证明语义。

后续顺序：定位原生正常下载/落盘流程 → 明确完成标志、加密/索引写入和清理规则 → 证实可由宿主调用且不会启动第二路播放 → 以临时测试缓存目录验证中断/损坏/账号和档位变化 → 检查重启后原生与插件都能正确命中，再决定接入。未完成前保持只读。

## 历史基线：已落地与平台差异

| 项目 | Windows 0.3.0 | Mac 0.2.5 候选 |
|---|---|---|
| 首曲入口 | 早期桥、2.5秒/32条初始化队列；读取宿主持久化配置 | 保留已有早期队列及首次输入授权等待 |
| 启动准备 | 通过原客户端授权解析器准备保存的当前行；等待队列恢复最多10秒；不发 Load/Play | 保留已有页面恢复快照与有效 Load 流程；允许暂停的已知授权曲目准备；完整进程恢复仍待实机 |
| 暂停预取 | 当前准备好后也预取可信下一首；实机确认暂停且activeNodes=0 | 去掉预取/准备对正在播放的依赖；调度仍检查播放意图；未实机 |
| 开关保存 | BetterNCM readConfig/writeConfig，写入后回读确认，串行更新并镜像页面配置 | 继续使用宿主 enabled API，沿用已有错误恢复路径 |
| 缓存 Worker | 共用 XOR/MD5 Worker 已接入，但客户端 CSP 禁止 Blob Worker；使用分块兼容路径 | 同一可选 Worker；宿主允许性和性能待实机 |
| 耗时记录 | 增加排队、读取/校验、解码、装载就绪等字段 | 共用资源阶段字段；平台控制耗时仍需补齐 |
| 系统媒体 | 原生桥与系统发布语义仍未全面验收 | 已知控制中心进度回跳未解决 |

Worker 使用固定版本 CryptoJS 4.2.0 core/MD5，源码和 MIT 许可随仓库提供；不加载远程代码。每次处理最多64KiB，传递可转移缓冲，结束/取消时终止 Worker；不传音源 URL、账号或凭证。Worker 创建被宿主安全策略拒绝时保留分块处理，不更改 CSP/浏览器安全策略。

## 时延与验收口径

分别记录以下指标，不能相互替代：

| 指标 | 边界 | 证据 |
|---|---|---|
| 首次响应 | 真实点击/自动恢复意图 → 第一份实际声音输出 | 客户端时间戳＋设备回录 |
| 授权解析 | 客户端请求源 → 返回本次授权资料 | 平台源解析器时间戳 |
| 排队 | 资源任务入队 → 开始读取 | resource-start.queueMs |
| 读取和校验 | 响应读流开始 → 完整身份校验完成 | decoded.readValidateMs，不含全部元数据查询时间 |
| 解码 | decodeAudioData开始 → 解码结果就绪 | decoded.decodeMs |
| 插件装载 | 截获Load → 输出准备完成 | Windows web-loaded.loadMs，不含此前授权解析 |
| 自动衔接调度 | 下一首预约开始 - 上一首PCM结束 | scheduledGapFrames，同采样率目标0帧 |
| 实际断音 | 设备输出连续性 | 系统/设备回录；不能用预约0帧代替 |
| 原生模型接认 | Web开始下一首 → 原生模型接受 | claim delay；不是装载时间或断音长度 |

应覆盖相同曲目/档位/采样率、冷启动与热缓存、网络无缓存、连续快速前后切歌、暂停恢复、读缓存失败、内存不足、换账号/档位、混合采样率、休眠/设备变化。报告样本数及p50/p95；当前少量实测只能作为案例，不能称为两端同速或整体最优。

## 本轮验证与下一步

见 [Windows 0.3.0记录](verification/windows-best-practices-0.3.0.json)。Windows 启动准备缓存约3秒，期间contextGeneration=0、原生Load/Play=0；暂停预取成功；关闭后立即强杀/重启仍为关闭。Worker的字节还原和正确/错误MD5离线检查通过，但Windows CSP阻止真正创建，不能声称已消除界面线程校验成本。

0.2.5 当时只完成修改文件语法和ZIP打包检查，未在当时的Windows电脑上执行Mac实机验收。0.2.5是开发候选，不能覆盖0.2.4的历史实机结论。

优先级：P0 两端控制竞态/恢复及故障回退 → P1 完整端到端测量与Mac实机 → P1 宿主允许的后台计算通道 → P2 原生缓存写回能力验证。共享协调器仍未完全抽取，不应为了形式上的“代码一致”复制平台特有协议。
