# 临时 Web Audio 桥接：新的实现边界

用户明确要求：Web Audio 只负责曲目衔接，完成后全部交还原生播放。这个要求优先于旧调研中持续使用替代播放后端的建议。本文是方案与可行性检查，不是已经实现的播放器功能；已安装 0.1.8 仍会持续接管兼容曲目。

## 目标流程

```text
原生播放 A
    → Web Audio 临时播放 A 尾部 / B 开头
    → 原生从 B 的对应位置继续
    → B 的正常播放由原生负责
```

正常播放、音源与音质选择、音量、设备、进度控制、系统媒体状态归网易云。插件只在一次曲目交接的短窗口内使用 Web Audio，不将失败的临时桥接延长成整首或整条队列的替代播放。

## 必须完成的两次交接

1. **进入桥接。** 原生继续播放 A，后台准备兼容的 A 尾部和 B 开头。只有 Web 输出已就绪、队列及源身份一致、原生 B 的准备路径可执行时才进入；临近边界才临时接管，不能在当前曲目准备好后就提前接管整首。
2. **离开桥接。** Web 连续播放到 B；原生在 Web 仍出声时准备 B、完成解码及定位。交还时必须对齐“将实际出声的 B 位置”，而不是早先发出 Seek 时的 Web 位置。确认原生能够从对应音频时刻连续出声后，才退出 Web 并释放其音乐资源。

不能简单设定“Web 播放 B 一秒后恢复原生”。原生装载、Seek、输出启动的时间会变化；固定延时或看到 RPC 成功，都不能证明设备已经输出。每首额外发生原生→Web、Web→原生两次切换，两处都需要验证没有缺帧、重复、重音或新增静音。

## 系统状态和取消

- 系统媒体会话始终由原生一方维护，显示实际音乐的逻辑状态。Web 只负责临时音频补位，不再建立与原生竞争的长期媒体会话。
- 原生底层为了准备 B 而暂停、Load、Seek，不能把这些内部动作发布成用户暂停，也不能提前把 A 的面板改成 B。
- 用户暂停、拖动、手动切歌时，取消当前交接，按用户的新意图恢复原生；旧曲目、旧代次的异步完成不能覆盖新操作。
- 若进入前发现不能满足交还条件，保持原生，当前边界不保证无缝。不能通过降音质、反复 Seek、交叉淡化或长期保留 Web 出声来绕过这个边界。

## 本机接口核对：目前还不能直接实施

2026-11-14 再次只读检查正在运行的网易云 3.1.12（3444）SDK：

| 所需能力 | 当前检查结果 | 后果 |
|---|---|---|
| 提前准备原生 B，不打断当前出声或错误推进界面 | `AudioPlayer.preLoad` 空实现；未验证到替代准备入口 | 不能把它当作原生解码就绪能力 |
| 查询原生输出位置与就绪情况 | `getPlaybackInfo` 直接返回空对象 | 缺少与 Web 输出对齐的已验证依据 |
| 原生 Seek 完成 | SDK 通过 RPC 和全局 Seek 通知返回位置 | 能用于普通恢复，不能单独证明实际出声已对齐 |
| 原生 Play 完成 | SDK 在 RPC 后返回 true | 不能单独证明首个音频帧已经到达设备 |
| 原生单独发布逻辑播放状态、隔离准备期间的内部暂停 | 尚无已验证的 JS 入口；原生 NowPlaying 更新绕过页面桥 | 临时桥接也不会自然消除系统图标闪动 |

现有 `restoreNative` 在事务开始调用 `stopCurrent()`，之后才 Load→pause→Seek→play。它是异常/关闭时的恢复路径，不能直接当作不中断声音的桥接退出路径。后续若实现，必须新增有明确准备与提交阶段的原生交接能力，不能只在 `claimed` 后定时调用它。

原生引擎内部存在跨流处理逻辑，但现有宿主与 SDK 没有连通已验证的准备/对齐接口，详见 [原生能力检查](NATIVE_GAPLESS_FEASIBILITY.md)。如果需要扩展原生桥，范围应只涵盖下一首准备、音频位置/输出就绪、系统状态所有权；不扩展主题、音效或音质功能。

## 当前状态与验证门槛

本轮只调整设计文档，没有修改或热加载音乐代码，也没有停用现有无缝插件。新的临时桥接尚未实现或安装，没有声卡/数字回录证明双向交接可连续出声。0.1.8 的系统闪动和回跳仍按 [已知问题](SYSTEM_SYNC_0.1.8.md) 保留。

实现后必须分别验证进入桥接、A→B 边界、交还原生三处，确认 B 后续由原生实际出声、Web 音乐节点和相关资源已退出、音质选择与原生 UI 一致，并核对暂停、拖动、手动切歌和准备失败的取消。Windows 同样遵守这个目标边界；它目前仍只有方案，没有可运行包。
