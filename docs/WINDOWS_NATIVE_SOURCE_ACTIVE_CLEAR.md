# 活动取数、快速 Seek 和统计复核

2026-11-15；Windows 3.1.43.205627，native-source-trial。安装仅用于实验，结束后恢复稳定 0.4.5。

## 真实活动清理

开始前备份原生缓存 27 文件、213541099 字节。选择一首新源进行 Web 播放，确认原生队列正在执行后台补齐（priority=10），然后通过实际 SDK 默认 clearCache() 清理：

- 清理约 142.1 ms 返回 true；七个 20 ms 采样观察到 clearing=true。
- 屏障期间原生 Load 增量 0；活动批次被取消，取消数由 2 增至 3。
- 清理后队列为空，代次从 1 增为 2，Web owns=true；没有恢复原生或缓冲失败事件。
- 当前工作 PCM 约 86.3 MB 保留。完成后新一轮下一首准备产生三个新缓存文件；这发生在完成通知之后，不是屏障内的旧任务补写。

测试后正常退出，并恢复原来的 27 个文件，逐文件 SHA-256 与备份一致；新实验歌曲缓存没有冒充原始备份。不能承诺清理后继续播放/预取也永远不再生成缓存。

## 清理后目标区间及连续控制

在当前曲磁盘数据已被清除的情况下，暂停状态 Seek 到 239.506 秒（距尾部约五秒），约 1459 ms 完成；Web 所有权保持、playingState=1，未自动播放。

随后以约 40 ms 间隔发出 110 → 25 → 180 秒请求。前两次控制回调约 43/71 ms 返回，最终 180 秒约 2583 ms 完成，只有最终目标产生新的等待完成记录。队列最终为空，仍暂停、Web owns=true。部分目标可能命中保留的 PCM，因此不能用前两次时间声称网络 Seek 是几十毫秒。

## 听音统计

暂停状态再 Seek 到 100 秒，发生两个原生取数批次。通过宿主正常 channel 查询当前歌曲 getPlayedTime：前后 playedTime 和 playedAudioTime 均为 27.040589569160996；仅位置百分比随 Seek 改变。这证明本次辅助取数没有污染宿主用于听音上报的当前歌曲计数，不证明所有原生内部遥测已经完成审计。

## 宿主输出能力

不改变安全设置，在当前页面检查得到 isSecureContext=false、crossOriginIsolated=false。虽然 AudioWorkletNode 构造名存在，实际创建的 OfflineAudioContext 没有 audioWorklet，未能进入 addModule/离线渲染。不能只凭构造名宣称 Worklet 可用。本机继续使用已就绪的不可变分块 AudioBuffer 排程，不为迁移 Worklet 放宽 CSP/协议安全设置。该探针不输出声音、不改变当前播放上下文。

## 索引复用优化

新的 native-byte-source 对同一音源保留已确认的有效区间；已覆盖请求不再每次重复读取 .idx。每次读仍检查音源键、长度和缓存代次；缺口重新读索引并经原生取数，清理使原有快照失效，取数结果不能越过清理代次提交。

临时内存检查确认：同源范围复用、不同源拒绝复用、在途读取期间清理会拒绝返回旧字节。修改文件语法及试验 ZIP 打包通过。新优化尚未完成实机耗时对比。

一次包含检查、复制试验包及带调试端口重启的组合命令被自动审批拒绝，原因仅为 blocked by policy；未执行该组合命令。之后只做独立内存/语法检查，并成功恢复稳定包、正常启动应用，没有重试被拒绝的组合操作。因此本轮不把新增索引复用描述为已完成运行验收。
