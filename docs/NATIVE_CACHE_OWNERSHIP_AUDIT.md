# 原生缓存所有权复核（Windows 0.4.5）

## 结论

当前实现不是“只替换输出设备、其余缓存完全原生”。受支持曲目由插件截获 Load/Play，独立读取、解码并通过 Web Audio 输出；原生负责授权、队列、界面和已有磁盘缓存管理。原生 Load 没有收到新曲目，不能推断原生仍按原有播放、拖动时机继续落盘。关闭开关、不支持或恢复时仍走原生，不是所有音频都被强制替换。

用户要求的目标应是原生拥有下载/缓存及有效区间，Web 仅消费相同音源的可读字节并负责解码、时钟排程。不能用额外整曲下载、静音的第二条播放链路或自写原生缓存索引冒充这一目标。

## 本机接口和文件证据

客户端 3.1.43.205627 的 SDK 暴露 storage.queryNewCacheTrack、queryNewCacheTracks、playCacheInfo、setPlayCacheConfig、audioplayer.setAudioStrategy、preLoad 等接口。查询/配置不等于“读取原生解码前字节”的接口。download.start 是通用下载任务接口，需要显式路径/类型，不能当作播放缓存接口直接使用。

客户端默认的范围策略包含缓冲阈值、请求间隔、片段范围、当前进度权重及下一首预加载条件；这说明原生具有分段缓冲调度。默认配置的存在不能证明当前实验组使用完全相同的参数，也不能把策略轮询间隔当作文件落盘时机。

对一首此前主要通过 Web 播放的授权歌曲进行检查：

- 完整缓存查询 cached=0，但已有原生 .idx/.info/.uc 文件；.idx 记录总大小 28631824 和有效区间 `0 4403199`。因此 cached=0 不等于没有任何磁盘数据。
- 在该区间的开头、中间和末端各读取 512 字节，按缓存 XOR 格式还原后，与当前授权网络源相同位置比对，三个样本均无差异。只证明这些样本，不足以证明所有索引情况都已适配。
- Web 播放短测前后 cached 仍为 0，桥没有转发原生 Load/Play。现有插件只接受 cached=100，所以未复用这些原生部分缓存。
- 原生播放对照中，getPlayedTime 增长约 5 秒，确认实际进入原生播放；完整缓存查询仍为 0。观察到 .uc 文件长度由 26427676 增至 28631824，但 .idx 区间未更新。文件长度增长不能证明整个文件所有区间已有效，也不能据此推断索引刷盘时机。
- 独立调用 SDK 对应的 preLoad 后，3.5 秒内没有观察到有效区间或完整缓存标记增长。此结果不能证明接口无效，但不足以用它实现独立的原生缓存数据源。
- 对照包含短时播放、暂停及跳转，没有完成原生完整播放周期或文件系统写入跟踪。未删除原生缓存，未修改原生缓存配置或落盘文件。

## 当前拖动行为

带有效索引的 FLAC：未准备位置优先读取对应范围，取消旧位置的后台准备；已解码直接复用，已下载编码区块直接解码。就绪后在同一音频时刻替换输出节点。返回已准备位置不会从头下载。

等待期间旧位置继续播放，这不等于原生界面的缓冲展示完全相同。缺少索引、范围请求失败等情形仍有顺序读取/原生恢复路径，不能承诺所有格式完全一致。

## 副作用与后续实现门槛

1. Web 网络数据只进入插件会话内存，无法保证重启后命中原生磁盘缓存。
2. 原生部分缓存暂未接入，可能重复读取原生已经缓存过的部分字节。
3. 0.4.5 的原生下一首预加载隔离用于避免双重获取，不能同时宣称原生下一首缓存流程完全照旧。
4. PCM 仍采用预算内整曲缓冲，当前播放工作缓冲在清缓存时保留。

下一步若实现原生缓存所有权，需要验证三个能力：按当前播放/Seek 意图让原生准备目标范围；获取同一授权音源的可读字节及有效区间；在不启动第二条音频播放链路的情况下保留原生缓存登记和落盘行为。验证通过后再让插件网络读取退出主要路径。

目前尚未验证到同时满足这些条件的 SDK 接口。本轮保留 0.4.5，不为模仿落盘时机新增写回或强制预下载。测试后恢复无缝开关开启，暂停播放，正常重启并关闭调试端口。
