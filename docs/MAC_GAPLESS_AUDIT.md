# macOS 无缝播放实现审查

> 历史基线：下文针对 0.1.0。当前 0.1.1 的修正、实机验证及保留限制见 [修正记录](REMEDIATION.md)。

日期：2026-11-14。审查对象：审查时实际安装的 `gapless-player-mac 0.1.0`，网易云音乐 3.1.12（3444）。下文源码位置与 SHA-256 均属于该历史版本，不指向当前 0.1.1。

核对结果：安装包中的 `player.js`、`startup_script.js` 与本地源码一致。本轮只读源码和客户端状态，没有改变正在运行的播放器、添加测试或执行应用构建。

## 结论

同一音频时钟提前预约下一首的方向成立；已有实际客户端播放成功记录。当前版本仍是针对本机客户端的早期实现，存在可以从代码路径确认的缺口，不能据一次正常切歌宣布所有场景可靠，也不能宣布输出链路与网易云原生播放器完全相同。

音质档位、授权音源和音量设置得以保留；解码、PCM 处理和设备输出经过 Web Audio，底层链路已经改变。「没有主动降低音质档位」和「与原生输出比特完全一致」应分别验证。

Windows 应复用修正后的共享核心，同时给 Mac 使用同一核心。下面列出的缺陷不应被作为“功能一致”的一部分复制。

## 本轮证据

- `mac/player.js` SHA-256：`141ccd7c20211a55182cb276b898520ea313142f68af7da93e8728908a1cdeb2`。
- `mac/startup.js` SHA-256：`2977fa03adb18b327f2ebfab5c890526bb4b3c4526c5a4eb1e1b5aa0dfa61a15`。
- 只读诊断再次读到《Baptized In Fear》→《Open Hearts》的预约、切换和原生 Load 接认，预约日志 `gapFrames: 0`，原生接认发生在下一首开始后约 146 ms。
- 两首返回规格为 44.1 kHz 无损，原有音质选择为 Hi-Res。下一首为不同采样率时，已有回退日志。
- 正常播放、暂停、拖动、歌词同步和重开成功是已有场景证据；以下竞态、失败路径没有通过故意破坏当前客户端进行现场复现。

下文「代码确认」指条件满足时可沿源码执行到问题分支；并不表示该条件已经在用户这台机器出现。

## 按优先级列出的发现

### D01 · P1 · 下载任务共同修改播放 AudioContext

位置：`mac/player.js:123`、`:164`、`:179`、`:268`、`:454`。证据类型：代码确认的竞态缺口。

当前曲目 A 的下载和下一首 B 的预加载可以并行。`audioContext(bytes)` 用全局 `S.ctx` 解码；只有 `S.current.owns` 或已有预约时才禁止不同采样率替换上下文。A 尚未接管时，B 可以创建或关闭上下文；A 的解码也可能仍在进行。

具体路径：B 先解码为 96 kHz 并进入缓存 → A 下载完成把全局上下文换成 44.1 kHz → B 缓存仍在 → `scheduleNext()` 直接取缓存，没有再核对 `entry.sourceRate / buffer.sampleRate / S.ctx.sampleRate`。因此当前“不重采样、异采样率回退”的保护可以被绕过。旧解码完成后使用新的全局上下文也有同类问题。

修正：播放上下文只由核心控制；解码任务使用独立、按源采样率创建的解码上下文；缓存保存源采样率、解码采样率、上下文代次。所有接管、缓存命中和预约都重新检查规格，异采样率始终走原生。禁止下载任务关闭播放上下文。

### D02 · P1 · 下一首未被原生接认时没有恢复资料

位置：`mac/player.js:247`、`:276`、`:316`。证据类型：代码确认。

预约候选创建时 `info: null`，音频边界到达后就变成 `S.current`。如果原生 Load 三秒内没有接认，或此前触发设置回退/关闭插件，`restoreNative()` 先停止 Web Audio、清除所有权，然后因 `!c.info` 直接返回。它没有执行原生 load/seek/play，也没有发送明确失败状态，会留下停声及 UI 不一致的路径。

修正：预约前必须准备有效恢复计划；保留上一份完整原生快照、候选曲目实例和原生选曲入口。在等待接认期间保持独立 handoff 状态。恢复资料不完整时禁止进入预约；异常恢复通过经过验证的原生选曲流程加载指定候选，不能再发 End 推进一次，也不能静默 stop 后返回。

### D03 · P1 · 控制命令和异步回调缺少实例/代次校验

位置：`mac/player.js:395`、`:404`、`:411`、`:327`、`:489`。证据类型：代码确认的缺口，实际旧命令来源需目标 SDK 捕获。

当前 play/pause/seek 只判断是否拥有播放器，没有检查命令对应哪一次播放。上一首或旧加载流程的迟到命令可能作用于已经开始的下一首。Seek 的延迟通知还读取全局 `S.token`；恢复 load 的回调没有检查用户是否已经换歌，会继续 seek/play 旧资料。

修正：区分曲目 ID、队列实例 ID、原始 playId，增加 loadEpoch、controlRevision、queueVersion、qualityVersion、contextGeneration。所有异步继续执行前核对代次。用户全局暂停在等待接认期间仍必须有效；旧流程的 seek/stop 不得作用到新实例，不能简单把所有旧 ID 命令一概吞掉。

### D04 · P1 · 首次接管和原生恢复没有完成握手

位置：`mac/player.js:290`、`:327`、`:489`。证据类型：代码确认的时序缺口。

首次接管先标记 owns、发原生 pause，随后直接把 Web Audio 排在当前上下文时间 +20 ms；没有等待原生暂停完成。原生恢复则在 load 回调内连续发 seek 和 play，没有等 seek 成功。如果原生命令或设备输出延迟较大，可能短时重复出声、出现空挡或从错误位置恢复。固定 20 ms 不能覆盖所有设备。

修正：采用具有超时和代次校验的 load/seek/play/pause 事务；在原生 SDK 的正确完成通知后确认后端交接，记录最终位置与实际状态。事务失败时回到可控的原生路径。首次原生→Web Audio 交接单独验收，不与已预约的 A→B 衔接混为一项。

### D05 · P1 · 512 MiB 预算检查发生在整首解码之后

位置：`mac/player.js:159`—`:170`。证据类型：代码确认。

现在先完整下载，再调用 decodeAudioData，最后才检查解码大小。超预算文件和多个并发解码已经分配内存；检查只统计 cache 中的 PCM，遗漏下载字节、解码副本、在途任务和仍被音源引用的已移出缓存 buffer。

双声道 float32 的五分钟音频约占：44.1 kHz 100.94 MiB，96 kHz 219.73 MiB，192 kHz 439.45 MiB。两首五分钟 192 kHz 音频仅 PCM 就约 878.9 MiB，超出预算时并不是“拒绝后才不会分配”。

修正：下载前按帧数/时长和采样率预留 PCM 预算；限制压缩字节大小及单个解码任务；统计在途预留和仍存活的音源引用；无法可靠估算就跳过预加载。512 MiB 可作为插件管理的内存预算，不应承诺整个客户端进程峰值一定低于该数值。

### D06 · P1/P2 · 队列预测没有实例标识与可信度

位置：`mac/player.js:179`—`:194`、`:268`。证据类型：代码确认的表达缺口；随机/心动算法一致性未全面验证。

通过 `row.id === current.id` 找第一条相同歌曲，再按 displayOrder/randomOrder 选下一行。重复曲目不能区分第几次出现，随机序列末尾、动态推荐及边界前的临时改队列也没有权威承诺。推错的候选已经在原生 Load 接认之前出声，事后纠正不能消除短暂播放错歌的事实。

修正：使用队列实例 ID 和 queueVersion；只接受原生可确认的下一首。无法确认随机/推荐结果时保持原生播放。预约后监听队列变化立即取消，边界及用户控制前根据音频时钟校正状态；模式支持不等于每个模式下所有边界都有可预约下一首。

### D07 · P2 · 预约依赖较短的主线程窗口，日志不是输出测量

位置：`mac/player.js:255`、`:268`—`:279`、`:471`。证据类型：代码确认；主线程卡顿下实际程度需实机验收。

每 150 ms 检查，只有剩余 1.5 秒到 30 ms 时才预约。主线程停顿超过窗口会错失预约。预约成功后音频线程可以按时续播，但 `onended` 中的曲目接认和 UI 更新仍可能延迟。

`gapFrames` 来自人为设定的 `next.start - current.end`，而两者被直接设为相同值；它没有测量声卡输出、解码首尾留白或实际调度提交时刻。日志显示 0 帧只能证明预约参数相同，不能证明听到的输出零间隔。

修正：下一首有效且解码完成后尽早预约，队列变化即撤销；通过 currentTime 在控制入口和状态心跳校正跨界状态，不只依赖 onended。记录提交余量、错过预约及 UI 接认延迟；正式验收另做已知连续素材的数字输出或回录分析。

### D08 · P2 · 缓存键与原生接认条件不够完整

位置：`mac/player.js:144`、`:359`、`:374`。证据类型：代码确认的校验缺口。

缓存键只有 `曲目 ID:请求音质`；原生接认只比较曲目 ID、请求音质字符串、实际 level。它没有区分账号代次、不同音源版本、编码、采样率、声道、native fileId/MD5 或音质改变后的过期请求。同一个 level 不能证明两次请求拿到相同音频。

修正：分开内容缓存和播放实例；内容键加入已验证的音源指纹、授权代次和规格。预约与接认都核对规格和内容标识；拿不到可核对指纹时降低预加载可信度，不宣称严格同一音源。登录状态及音质修改令相关请求失效。

### D09 · P2 · 非运行音频上下文缺少显式恢复状态

位置：`mac/player.js:239`、`:395`、`:444`、`:472`、`:495`。证据类型：代码确认的缺口。

拥有播放时若上下文 suspended/closed，play 调用仍会被消费并回复成功，即使 `startCurrent()` 返回 false。未订阅 statechange/error，也没有睡眠/输出设备改变后的恢复事务。页面卸载时发送的异步 load/seek/play 不保证都能在页面生命周期结束前完成。

修正：只有确认音频开始或合法继续播放后才确认成功；context statechange 进入独立恢复状态，保留用户播放/暂停意图。重开使用已持久化的最小播放快照，由新页面主动恢复；不能依赖卸载回调完成多阶段原生事务。

### D10 · P2 · 永久不兼容仍每 30 秒完整重试

位置：`mac/player.js:303`—`:314`、`:139`。证据类型：代码确认。

采样率不兼容、格式不支持和网络错误共用固定 30 秒重试；采样率判断在完整下载后，长曲目期间可能重复下载同一首 Hi-Res 文件。nextTrack 为空时直接 return，未执行清理和取消过期任务。

修正：将不兼容/权限与临时网络错误分开；不兼容在相关上下文、音质或授权变化前不重试；网络错误有限指数退避。所有队列更新包括“无下一首”都执行请求和缓存清理。若原生网络接口不能取消实际传输，忽略旧结果也必须保留相应内存预留到完成。

### D11 · P2 · 内部模块和固定时间歌词补丁容易随版本失效

位置：`mac/player.js:38`、`:58`、`:69`、`:86`、`:94`；`mac/startup.js:16`、`:51`。证据类型：版本耦合及异常恢复缺口。

依赖 React 私有节点、Webpack 4 载入方式、压缩源码正则、私有暂停字段和固定 250 ms 的歌词刷新。歌词 Promise 返回后没有再次确认曲目仍为同一实例。桥接 handle 调用也没有异常保护：在修改 owns 或暂停原生之后抛错，可能打断原生命令链。

修正：平台适配器先完成能力检查和契约校验，再允许接管；未知版本失败时保留原生。歌词按原生数据准备完成通知刷新，异步返回后复核实例代次。拦截层采用异常回退及恢复所有权的事务，宿主/SDK 更新后只恢复本插件仍拥有的包装层。

### D12 · P2 · 输出规格与收听时长的诊断信息不充分

位置：`mac/player.js:262`、`:431`—`:438`。证据类型：字段来源确认；原生时长语义需要进一步捕获。

getPlaybackInfo 将解码 buffer 的采样率、声道和 32 位 float 信息同时当作 deviceAudioFormat 返回，并没有查询真实输出设备格式。End 的 playedTime 固定为整首 duration，未记录暂停/拖动后的实际收听时间；若目标 SDK 按该字段结算实际收听，会产生不准确统计。

修正：区分源音频格式、解码 PCM 格式和设备输出格式；未知设备信息不伪造为已测结果。按目标 SDK 捕获并验证 playedTime 的语义，分别维护播放位置、累计听音时间、时长，协议单位由平台层转换。

## 原理本身的边界

Web Audio 的定时开始机制适用于同一时钟的连续调度。decodeAudioData 会按上下文采样率解码/转换；上下文与设备采样率不同还可能在输出端转换。AudioBuffer 的脚本表示为 float32。因此只设置源采样率不足以证明端到端不重采样，也不足以证明与原生输出相同。[W3C Web Audio 推荐标准](https://www.w3.org/TR/2021/REC-webaudio-20210617/)

没有裁剪作品留白是本次产品要求；MP3 编码器填充是否被具体 Chromium 解码器正确处理，仍需要素材和客户端版本验证。默认不能用波形静音检测裁剪内容来“做出无缝”。

异采样率、特殊音质/音效、试听权限、预加载来不及，继续使用原生播放是功能边界；跨平台需要对齐这些回退规则和可见状态，而不能承诺所有曲目无条件无缝。

## 修正顺序

1. 先处理 D01—D05：上下文所有权、恢复计划、命令代次、原生握手和解码预算。
2. 处理 D06、D08、D09、D11：权威队列、音源校验、生命周期及能力检查。
3. 补齐 D07、D10、D12 的调度诊断、请求策略和原生协议字段。
4. 让 Mac 和 Windows 共用同一修正核心；平台层仅转换协议、获取原生状态和放置开关。
5. 在两个实际客户端分别做正常播放和故障路径验收，再发布“功能一致”的版本。

本轮没有修正或部署上述代码问题；已有成功场景仍成立，覆盖边界已在本报告收窄。
