# 0.1.12：输出交接卡顿修正

2026-11-14。网易云 Mac 3.1.12（3444）、BetterNCM-mac 0.1.7；保持曲尾/曲头临时桥接，普通播放交还原生。当前输出设备的短时音频回录证实存在实际交接缺陷，不能把它解释成正常无缝播放。

## 已定位的问题

- 0.1.11 的原生暂停通知并不代表音频已停止。回录中 Web 已出声，而原生还输出约 150–170 ms；两路同曲目约相差 20.65 ms，产生叠音和声音变化。
- Web → 原生输出选择只补偿音量 RPC 耗时，回录中存在约 21.92 ms 的新增双声道静音。
- 在 `currentTime` 立即启动节点，没有为在途渲染回调留出提交时间；原生进度报告/累计计时也不能当作连续设备采样时钟。
- 原生已运行时重复 Seek，再把量化累计计时读数作为新锚点，会出现“估算已对齐、实际重复一段声音”。不能通过增加运行中 Seek 次数解决。

## 修正

1. 原生继续出声，Web 节点提前约 80 ms 预约静默起播；源偏移同步前推到预约输出时间，避免从过期的 `currentTime` 起播。
2. 进入桥接前用最近 1.5 秒的多个原生进度报告拟合连续位置，检查稳定性。Seek/播放状态变化清空旧样本；样本不足或不稳定保持原生。移除不再使用的单次累计计时锚点。
3. 原生 → Web 在预约边界选择声音输出，再暂停已静音的原生。原生输出保持静音，直到下一首已静默装载并确认暂停；不能在 pause 通知到达时立即恢复音量，让残留输出重新叠加。
4. 当前客户端的回录验证了输出控制与设备时间戳之间约一个渲染缓冲的时差。用 Web `baseLatency` 与控制耗时构成该版本的校准模型，并对原生累计计时作相应输出补偿。**这是本客户端实测模型，不是原生公开设备时钟，也不能直接移植 Windows。** 缺少有效延迟信息时不强行桥接。
5. 原生交还以约 4 ms 的估算误差为校准目标；每次重试先重新静默装载原生，再从确认暂停的 Seek 位置建立锚点。最多三次，25 ms 仍为拒绝不稳定交还的外层门槛。Web 在准备和校准期间持续出声。
6. 到达预约输出边界后才关闭 Web 上下文，避免提前关闭仍有输出在途的音频设备。
7. 在 A 尾部拖进度/暂停，先把仍有内部暂停事务的原生 A 重新静默准备，再交还。音量恢复使用最新用户值；取消、超时、关闭和刷新仍有恢复处理。音量恢复 RPC 失败后仍继续释放 Web 节点/上下文，原生音量走既有恢复重发与日志处理，不能让一次恢复错误阻断清理。

没有添加交叉淡化、混音、EQ、静音裁剪、音质选择或窗口 CSS。输出选择只决定哪一路出声，网易云的用户音量和音质设置保持原有语义；全原生引擎接入仍需另行验证。

## 验证方法与边界

使用 Apple ScreenCaptureKit 已授权的应用级音频过滤，只采集网易云输出；未采集麦克风。注册的屏幕输出只维持流，画面直接丢弃，不写图片。音频与 PCM 参考仅在本机临时分析，不提交歌曲、缓存、账号或授权 URL。

捕获实际为 48 kHz 双声道 Float32；两首源为 44.1 kHz lossless。用同源解码参考、短窗口归一化相关定位交接前后的音乐位置，并检查双声道近零片段。采集样本的展示时戳用于对齐，采集层自身的不连续单独列出；不能把采集丢帧算成播放器断音。声音自身留白不被裁剪。

基线与修正结果、控制场景见 [验证记录](verification/mac-output-handoff-0.1.12.json)。两首仍为 Baptized In Fear → Open Hearts，实际完成 Web 预约跨曲以及原生 B 接管；音乐节点/上下文在交还后退出。

| 应用输出观测 | 0.1.11 基线 | 最终安装的 0.1.12 |
|---|---|---|
| 原生 → Web 音乐位置变化 | 约重复 20.65 ms，另有约 150–170 ms 原生残留叠加 | 约前移 4.81 ms，未再观察到原来的长叠音窗口 |
| Web → 原生音乐位置变化 | 约重复 30.21 ms | 约重复 3.77 ms |
| 双向交接窗口最长双声道近零段 | 0 / 21.92 ms | 0 / 0 ms |

另一轮相同正常交接逻辑的回录为约前移 3.69 / 1.10 ms，交还窗口存在约 0.71 ms 近零段。结果存在波动；这些值用于确认旧缺陷被明显压低，不是所有设备绝对无静音的承诺。音量恢复错误清理的最终增量在最终安装包上另做双故障注入验证。

实际 SDK 操作确认：桥接期间拖到 70 秒后交还原生，暂停时拖到 120 秒仍保持暂停；桥接尾部暂停、继续、上一首和下一首均执行一次。交接期间音量改为 41% 后恢复值正确；故意让输出关闭和音量恢复 RPC 各失败一次，原生继续播放，节点/上下文释放，音量恢复至 48%。验证结束恢复 Open Hearts 14.12 秒暂停、音量 48% 和原喜欢列表。系统面板闪动仍是下述未彻底解决项。

**应用输出回录覆盖系统混音链，未覆盖 DAC、扬声器、蓝牙链或声学回录。** 仍有数毫秒的位置误差和亚毫秒片段，不能宣称所有设备采样级零间隔。`baseLatency` 本来描述 Web 的输出处理延迟，不能单凭它证明原生延迟；此处须结合本机回录理解。[W3C 延迟定义](https://www.w3.org/TR/2021/REC-webaudio-20210617/#dom-audiocontext-baselatency)

macOS 系统媒体卡片的图标闪动、原生自身的进度回跳继续作为已知边界；本轮没有宣称全修复。Windows 只有一致实施方案，还没有实现或设备验收。

只执行增量 JavaScript 语法、包/源码一致性、真实客户端控制和短时输出分析；没有新增测试用例、全项目 lint/TypeScript 检查或应用构建。
