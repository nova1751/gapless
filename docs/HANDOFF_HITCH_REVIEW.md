# 0.1.4：临近衔接卡顿与输出冷启动

日期：2026-11-14。网易云 Mac 3.1.12（3444）、BetterNCM-mac 0.1.7、macOS 26.6.2 arm64。本机已安装并加载 0.1.4，旧包 0.1.3 保留备份。

临近衔接时听到停顿是需要修复的问题。不能把它视为正常无缝播放，也不能以预约/接认成功或 UI 正常来否定用户听感。本轮找到并修正一个输出冷启动缺陷；尚未回录声卡，不能认定它是所有偶发停顿的唯一原因。

## 发现

最近多轮接管发生在曲目结束前约 3–20 秒。接管与真正跨曲边界是两个时刻：前者切换原生和 Web Audio 后端，后者在已准备的同一时钟内开始下一首。0.1.3 允许临近结尾接管，因此首次交接产生的空挡也可能被听成切歌前卡顿。

实机在原生 Load、Seek 到 Baptized In Fear 的 220 秒后测量首次交接：原生 pause RPC 约 1.5 ms，暂停状态通知后到 Clock.start 调用约 0.6 ms，其中 getPlayedTime 约 0.5 ms。查询不是这次主要等待来源，未为了猜测而改变听音计数算法。

真正可疑的状态是：暂停原生、启动当前/下一首节点时，AudioContext.currentTime 和 getOutputTimestamp 的两个字段均为 0。running 状态没有证明输出已经处理首块音频；标准规定尚未处理音频块时输出时间戳为零。[W3C Web Audio 标准](https://www.w3.org/TR/2021/REC-webaudio-20210617/)

数据见 [修正前时序](verification/hitch-before-fix.json)。这里测量的是调用及输出时钟状态，不是声卡最后一个可听帧到下一帧的实际间隔。

## 0.1.4 修正

- PlaybackClock.open 在原生仍播放时等待输出时间戳相对初值推进。上下文、状态及音频规格保持有效，最多等待 500 ms；失败保持原生，不先暂停。
- 输出就绪后仍复核原有曲目、队列、控制代次及剩余时间；原生已经暂停则取消接管。外部暂停可能只产生原生状态事件，不能仅依赖插件命令入口更新 controlRevision。
- 不添加波形、混音或声音包络处理，不改音源、采样率、音质配置、音量或 UI。500 ms 是准备阶段的超时，期间原生继续播放；不是在声音停住后等待 500 ms。

500 ms 准备超时和原有至少剩余 0.12 秒的异步复核仍可能使非常晚的准备保留原生；不能为了无条件接管去掉这些保护。输出就绪检查只发生在接管准备期间，不是新的常驻分析任务。

## 界面线程与声音的区别

实际跨曲附近仍观察到约 124 ms 的界面线程长任务，补充 CPU 采样中约 128 ms。374 首队列下，2.667 秒采样的 updateEnvironment 自用采样时间约 3.75 ms；较多采样落在原生 bundle、运行时及 GC。自用时间不包含全部被调用工作，不能据此宣称插件总体耗时只有 3.75 ms。数据见 [CPU 采样摘要](verification/hitch-boundary-profile.json)。

这说明 UI 切歌仍可能有短暂卡顿；对应的实际音频缓冲没有静音，不等于声卡一定无停顿。没有为了隐藏 UI 卡顿改变网易云的队列、进度、样式或渲染流程。CPU 采样本身增加开销，结果只作局部定位。

## 确认范围

本轮修正避免在输出尚未启动时先暂停原生，不保证两个后端之间完全透明。输出本身仍有设备延迟，实机 API 返回约 56 ms；原生最后一个可听帧没有回录，不能将 API 时刻差直接算成实际静音间隔。设备切换、系统休眠、全部手势和所有曲目未穷举。

临时监测、时序包装及 CPU 采样已停止并清理，音质配置仍为 1999，音量仍为 0.48；最终状态见 [运行记录](verification/mac-0.1.4-final.json)。发布包、安装包与源码一致性见 [SHA-256](verification/PACKAGE_SHA256.json)。仅执行变更 JS 的语法、JSON、局部差异及打包一致性检查；没有新增测试用例、全项目 lint/TypeScript 或应用构建。

Windows [方案 v6](WINDOWS_GAPLESS_IMPLEMENTATION.md) 同步输出就绪和外部暂停保护；Windows 插件尚未实现。
