# Windows 0.3.1：优先消除整首解码起播等待

## 问题与策略

0.3.0 截获冷曲 Load 后，等待完整缓存/网络读取、MD5 校验与 decodeAudioData 才出声。Open Hearts 的一次装载为 5171 ms（读取校验 4250 ms、解码 570 ms；各指标边界不同）。预创建 AudioContext 不能解决整首等待。

0.3.1 对未准备好的 Load 同步放行给网易云，不创建该曲的阻塞 Web 解码任务；初始化也不再暂存播放请求。已确认兼容且完整解码的曲目才在 Load 时选择 Web。暂停恢复不将已采用原生的曲目改成 Web，避免同曲音色/后端切换。

原生起播至少 1.5 秒后，后台只探查完整网易云缓存或已授权本地文件。确认两首采样率、声道、已知位深相同后才完整校验/解码，失败或缓存未完成最多探查四次，间隔 15 秒。MP3 的未知位深不符合此保守的首次成对准备条件。已在 Web 链路内的下一首仍按内存→原生缓存→同授权音源预取，并检查规格。不会降低网易云选定的音质。

保留 Stop→下一曲 Load 之间已准备的缓冲，避免刚准备好就被清理。关闭释放资源；所有异步结果仍检查曲目实例、账号、档位与队列。完整校验要求不变，不修改样式、窗口按钮或开关布局。

## 诚实的边界

- 冷歌由网易云原生流式播放；本版不是 Web 流式解码器。
- 第一首原生→后续 Web 的边界不保证无缝。只有已准备好的连续 Web 曲目才按同一音频时钟预约。
- 手动选曲从零开始；自然衔接中 UI 接认稍晚时，不能把已经实际播放的下一曲重新归零。
- 缓存探查不证明完整性，完整 MD5/规格校验成功之后才能交给 Web 输出。
- Windows Chromium 91 实测 AudioDecoder 不存在，AudioWorkletNode 存在。前者缺失不代表不能实现流式；需要另行验证增量解码器、宿主 CSP、PCM 队列、缓冲不足、Seek、取消、FLAC/MP3 精度及校验策略。
- 后续 Web 流式目标：同授权音源/缓存→增量解码→有界 PCM 队列→单输出时钟。不得简单串联两个 audio 元素就宣称采样级无缝。
- Mac 0.2.5 未改动、未实机验证，不宣称与此次 Windows 策略相同。

## 本机验证

Windows 3.1.43.205627，BetterNCM 1.3.4，0.3.1 候选。

| 曲目/场景 | 选曲到原生 Load 通知 | 选曲到原生 Playing 通知 | 首次进度 |
|---|---:|---:|---:|
| Intoxicated，Web 缓冲未准备 | 530 ms | 593 ms | 0 s |
| Baptized In Fear，手动切换 | 112 ms | 181 ms | 0 s |
| Open Hearts，手动切换 | 106 ms | 163 ms | 0 s |

另一次 Baptized In Fear 的冷 Web 状态起播：Load 217 ms，Playing 285 ms，首次进度 0。之后后台成对准备完成，Open Hearts 命中解码内存，Web 装载 152 ms，web-start.offset=0；暂停后 activeNodes=0。Open Hearts→Moth To A Flame 的同规格预约 scheduledGapFrames=0。

以上是客户端事件/预约证据，不是声卡回录或全部曲目 p50/p95；磁盘缓存不是冷磁盘，未清空用户歌曲缓存。未测 Mac、网络极慢、DAC/蓝牙输出及所有本地格式。检查采用增量 JS 语法与 ZIP 打包，没有新增常驻测试。

补充：已准备的 Baptized In Fear 手动重入 Web 装载 40 ms、offset=0；Seek 到曲尾后实际经过 Baptized In Fear→Open Hearts，预约间隔 0 帧，宿主接认约 156 ms，暂停后活动节点归零。此处没有系统回录。最后补充了已授权本地文件的头部探查路径，该路径仅完成代码/语法检查。
