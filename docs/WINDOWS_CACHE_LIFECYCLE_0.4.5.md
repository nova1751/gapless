# Windows 0.4.5：清理联动与原生预加载隔离

## 原生清缓存联动

从本机 3.1.43.205627 SDK 确认，缓存清理使用 storage.clearCache，结果通过 storage.onclearcache 回传。桥在用户发起清理时同步清理插件缓存，原命令和原生结果继续原样交给宿主，不替换成功/失败状态。

清理取消跳转准备、下一首候选与最近播放缓存，清空编码区块和旧磁盘挂载映射。未使用的 PCM 立即释放，仍被取消任务引用的 PCM 在最后一次 unpin 时释放，并禁止重新命中。保留当前正在使用的播放缓冲（包括暂停后的当前曲），避免清缓存导致断音或丢失播放位置；这部分属于当前播放工作状态，不能宣称所有音频内存已经归零。

当前索引曲目后续缺失区块改从同一授权网络 URL 获取，避免继续访问被清理的磁盘文件；本地用户文件不被改写或删除。下一首准备短暂延后，临近曲尾或用户再次 Seek 时恢复及时准备。后续正常播放会重新产生缓存，这是新数据，不是旧缓存未清干净。

没有新菜单或插件。诊断对象 clearMemoryCache() 只运行插件清理部分，不删除原生磁盘缓存。关闭无缝开关和退出应用仍可释放插件的播放资源。

## 避免重复原生预加载

本机 SDK 的 audioplayer.onFetchPreloadInfo 请求由前端解析下一首音源，再通过 audioplayer.setFetchPreloadInfoResult 回传；成功/失败码分别为 1/0。Web 已持有播放且不处于恢复事务时，插件对此请求返回原协议的失败码和空音源，避免再次向原生提供下一首下载地址。已在途的迟到成功结果同样清空音源并返回失败；未接管或正在恢复时继续放行。

新增无敏感内容的请求/抑制计数，结合既有原生 transport 计数区分真实转发与 Web 合成事件。没有猜测未知的 stopDownload 接口，没有关掉用户下载任务，也没有把静音等同于停止网络请求。

## 验证

- 临时隔离桥检查：一次 storage.clearCache 请求触发一次插件清理，原命令只转发一次；原生结果仍交给宿主回调。未为测试删除用户现有磁盘音乐缓存，未完成真实设置按钮到磁盘删除的端到端验收。
- 运行中的插件清理：held 从 166080784 降到 81911840 字节；编码缓存从 1287800 降到 0；等待取消任务释放后 reserved=0，仅保留当前曲工作缓冲。
- 清理后 Seek 到 Baptized In Fear 的 229.176 秒：目标准备约 155 ms；Open Hearts 提前约 2.901 秒排程，scheduledGapFrames=0，boundary/claimed 正常，无回退。另一次清理后读取检查确认缺失区块转向网络，不再使用旧磁盘入口。
- 该运行原生 transport 的 Load/Play/Seek 均为 0，Stop 为 1；未收到真实原生预加载事件。对预加载事件及迟到结果的受控注入检查均返回空 info、code=0；检查时替换原生出口，未发送模拟音源给实际播放器。
- 以上不构成全进程网络审计，不能排除其他原生后台任务或接管前已开始的下载。只能确认本次桥转发和已识别预加载通道的行为。
- 修改文件语法、ZIP 打包和运行包校验；未做新的音频回录或 Mac 实机检查。

## 保留边界

原生与 Web 仍未双向共享新增磁盘缓存；没有写回未经验证的原生缓存索引。PCM 仍为预算内整曲 AudioBuffer 布局，未改为可独立淘汰的 PCM 分块。已解决的是缓存生命周期和已知预加载通道，不能称为整个原生网络栈已完全停用。Mac 行为未改变。
