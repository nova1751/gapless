# 0.1.3：Baptized In Fear → Open Hearts 间隔排查

这是 0.1.3 的历史记录。后续用户反馈临近衔接偶尔卡顿，0.1.4 修正输出冷启动就绪检查，见 [卡顿排查](HANDOFF_HITCH_REVIEW.md)。这里的缓冲证据不覆盖首次原生后端交接。

日期：2026-11-14。网易云 Mac 3.1.12（3444）、BetterNCM-mac 0.1.7、macOS 26.6.2 arm64。本机已更新并加载 0.1.3，保留 0.1.2 备份。

用户反馈有间隔感是有效的失败反馈。此前「预约时间相等、原生接认成功」只能证明协议执行，不能证明听到的声音连续。本轮修正了会错过接管和反复加载的具体问题，并验证两种场景的实际 Web Audio 渲染缓冲连续；没有测量声卡输出，也没有完成用户听感的最终确认。

## 发现与修正

| 问题 | 证据及 0.1.3 修正 |
|---|---|
| 临近结尾准备好了也无法接管 | 旧入口要求至少剩余 2 秒。修正前最近两轮这对曲目的下一首 Load 均发生在 `native`，没有该轮 takeover/scheduled；其中一轮从下一首解码完成到下一首 Load 仅 0.988 秒，已错过旧门槛。入口缩为 0.5 秒，每次异步等待后须至少剩余 0.12 秒，保留预约 0.08 秒提交检查和取消后恢复原生的保护 |
| 暂停清掉已准备的下一首 | 旧预取逻辑把「正在播放」与「应保留候选」绑定，暂停后丢掉 buffer，Seek 到结尾再继续又要下载/解码。改为按可信队列保留当前与下一首；暂停不新发下载，已有任务按原预算/取消规则完成 |
| 同曲目 Load 到 play 之间清掉暖缓存 | 旧 Load 只保留当前引用，异步准备又要求原生已播放；中间状态更新可清掉下一首和未同步采用的当前 buffer。Load 立即复核账号、请求档位、实际档位及源指纹，采用匹配缓存并保留可信下一首 |

上述协议时间不能直接当作声卡剩余播放时长；另一轮解码到 Load 相隔 2.137 秒，仅能确认未接管，不能凭此单独确定门槛原因。[修正前音源及协议记录](verification/audible-gap-before-fix.json) 也保留更早的预约/接认成功记录，避免把不同播放轮次混在一起。

没有更换授权源、写改音质或音量设置，没有淡化、静音裁剪、响度分析或新界面。采样率、权限、可信队列、内存预算、实例及恢复保护继续有效。缓存保留会使暂停期间仍占用已准备的内存，本对曲目为 164,792,984 字节，约 157 MiB；预算仍为 512 MiB，关闭及队列/账号/档位变化仍执行清理或失效。

## 实际渲染验证

在播放增益节点增加临时被动监测分支：立体声先分成两个通道，各用 32,768 帧 AnalyserNode 读取最近波形，监测输出不连接声卡；原增益到 destination 的连接保留。先确认正常音乐能读到有效信号，再读取跨曲前后各 200 ms 的窗口，只保存统计值，不保存音频。该 API 的最近波形、环形历史及读取行为依据 [W3C Web Audio 标准](https://www.w3.org/TR/2021/REC-webaudio-20210617/)。

按两通道每帧的最大绝对值统计精确零及低于 −100 dBFS 的连续帧。窗口包含 17,639 帧，两个场景均完整覆盖边界；时刻与采样帧对齐有一个渲染量子附近的误差，因此不把快照边界宣称为设备级精确测量。

| 实机操作 | 实际缓冲结果 | 协议及节点结果 |
|---|---|---|
| 已接管时暂停；暂停 Seek 到最后 1.2 秒；立即继续 | 最大连续精确零帧 0，最大连续低于 −100 dBFS 帧 0；5 ms RMS 约 −15.83 到 −11.63 dBFS | Seek 后保持暂停；缓存不丢；只启动当前/下一首两个节点，下一首与当前结束相同，0 帧预约间隔；221 ms 后原生接认未重启节点 |
| 暖缓存下经正常桥强制同曲目原生 Load；原生 Seek 到最后 1.2 秒；立即继续 | 最大连续精确零帧 0，最大连续低于 −100 dBFS 帧 0；5 ms RMS 约 −15.83 到 −11.64 dBFS | Load 后仍保留两首约 157 MiB 缓存；400 ms 稳定后接管时实际约剩余 0.667 秒，旧 2 秒门槛会拒绝；214 ms 后原生接认未重启节点 |
| 已接管时 Seek 到最后 1.2 秒，继续采样到接认之后 | 边界前 200 ms 至后 400 ms，共 26,459 帧；完整覆盖接认，最大连续精确零和低于 −100 dBFS 帧均为 0 | 约 141 ms 后原生接认；接认后仍有有效音频，没有在 UI 接上时新增静音 |

第二个场景直接通过既有原生桥发 Load，用于确认原生路径和暖缓存，不将其称为鼠标重选的完整验收。首次原生与 Web Audio 交接发生在此窗口之前；上述缓冲没有采集原生输出。

记录：[暂停 Seek/继续](verification/rendered-ring-pause-resume.json)、[原生 Seek/重新接管](verification/rendered-ring-late-seek.json)、[包含接认之后的完整窗口](verification/rendered-ring-after-claim.json)。前两轮的 400 ms 窗口并未覆盖 214/221 ms 的接认，所以补充第三轮 600 ms 窗口。临时 start/stop/bridge 记录只保留 ID、时刻及阶段，节点记录在边界附近没有 pause/stop 或重复启动。原生接认只是让 UI 接上已经播放的下一首，没有让音频等待接认。

第一轮曾用 ScriptProcessor 分支采样；虽然收到的块没有静音，但界面线程阻塞导致采样记录之间缺失最多 6,528 帧（约 148 ms），不能据此判断声音连续或断流。该轮是证据不完整，保留在 [第一轮记录](verification/rendered-bus-pause-resume.json)，以后续完整环形快照作为本轮缓冲证据。

补充诊断曾用错本客户端的 webpack 注入格式，产生一个无效的临时待加载项；已删除该诊断项，恢复加载队列，并用正常队列选曲、Load 和接认确认恢复。该调用不在插件源码中，临时监测包装也已撤销。

## 确认范围与剩余问题

- 以上只能确认这对曲目、两种操作的 Web Audio 渲染缓冲未新增静音间隔，不能宣布用户听到的所有间隔已消失。声卡/驱动输出、首次原生→Web Audio 交接、异常恢复及主观听感仍未验证；首次交接本身仍可能产生短暂空挡。
- 最后 0.5 秒才准备好的源仍不接管；异步等待后不足 0.12 秒则取消并恢复原生。下载和解码来不及、不同规格或权限不兼容时仍可能有原生间隔，不能靠降音质或裁剪绕过。
- 之前的授权源观察中，Open Hearts → Moth To A Flame 出现不同采样率且后者超过单文件预算，属于原生回退边界。该限制针对当时的源规格，必须逐次读取，不能按歌曲 ID 固定推断。该曲目不属于本对曲目的成功范围。
- 临时监测分支和原型/桥包装已移除，播放继续在 Open Hearts；Hi-Res 配置仍为 1999，音量仍为 0.48。CUA 观察首页、歌单及播放条保持网易云原生布局及样式；没有修改 CSS/歌词界面。最终状态见 [运行记录](verification/mac-0.1.3-final.json)。
- 本版源码、发布包和当时安装包一致性见 [SHA-256 记录](verification/PACKAGE_0.1.3_SHA256.json)。仅执行变更 JS 语法、ZIP/源码、JSON 和局部差异检查，无新测试用例、全项目静态检查或应用构建。

Windows [方案 v5](WINDOWS_GAPLESS_IMPLEMENTATION.md) 已同步缓存、期限和真实音频验收要求；尚未实现 Windows 插件。
