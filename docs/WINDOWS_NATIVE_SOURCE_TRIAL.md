# Windows 原生数据源试验包

日期：2026-11-15。基于 Windows 0.4.5，属于独立评估模式，不是新的正式发行版本。用户要求任意位置优先起播，同时后台补齐整首原生缓存。

后续已发现并修复曲尾 Seek 欠载，完成一次双曲系统回录及暂停状态下的原生默认缓存清理/恢复。见[声音与清理验证](WINDOWS_NATIVE_SOURCE_AUDIO_AND_CLEAR.md)。活动下载期间的清理屏障等仍待验收，下文保留首次集成证据。

## 已接入

- `native-cache-queue.js` 串行调度原生实例：Seek 100、当前播放 60、下一首 30、后台补齐 10；高优先级可取消低优先级。清理递增代次、取消活动及待执行任务，等待旧会话 finally 结束后才允许新批次。
- `native-cache.js` 新增只读索引快照及有效区块读取，目录来自宿主设置，文件身份匹配已授权源；读取前确认 .idx 覆盖，读取后复核清理代次。
- `native-byte-source.js` 从原生缓存提供 FLAC 头部和后续范围；没有直连音频 URL 的分支。缺口经队列原生 Load/Seek/Stop 准备，再重新检查索引。失败交还原生，不能静默启动另一条 Web 下载。
- 主协调器在取数前取得既有原生静音门控，先隔离辅助实例通知；恢复、离开当前曲和清理会取消任务。宿主进度仍由 Web 时钟提供。
- 播放前方 PCM 约六秒安全水位满足、没有更高优先级取数时，低优先级逐批补齐当前曲的磁盘缺口。依据 FLAC 帧索引定位，不按文件大小线性估算时间。拖动/暂停取消补齐，不改变 Web 位置。
- 清缓存后原生数据源继续走原生，不能被旧缓冲清理逻辑改回网络 URL。

## 本轮实证

1. 临时协议检查确认队列最大活动数 1；高优先级抢占低优先级，清理后待执行任务未启动。
2. 真实原生会话测试：低优先级 100 秒取数被 150 秒高优先级任务抢占；前者返回 native-cache-preempted，后者完成，总耗时约 795 ms，Web owns=true。
3. 活动和待执行任务同时 clear 后均返回 native-cache-cleared；队列为空、原生活动会话为空、缓存代次递增。没有执行原生磁盘删除，因此不是完整清缓存验收。
4. 从此前有效范围 `[0,6641684)`、`[13591884,26684744)` 的部分缓存读取约 61.997 秒处未缓存区块。原生补入 219904 字节；Web 解码得到 88064 个每声道采样，与索引预期一致，错误 0。再次读取该区块不增加原生批次数。验证脚本第一次取到数据后因访问不存在的 errors.length 字段报错；改为可选字段后核查成功，未把该脚本错误算作解码失败。
5. 试验包真实播放完整缓存曲目，Web 首次准备约 822 ms；另一部分缓存曲目约 415 ms。缺口读取曾遇到 seek-range-unsupported，定位为本地 .uc 物理长度小于最终音源长度。
6. 修正范围校验后，试验包另一次部分缓存曲目首次准备约 913 ms，Web 保持 owns=true；原生后台补齐后 cached=100，原生索引覆盖全部 26684744 字节，整文件 XOR 还原后的 MD5 与授权源一致。原生计数 Load 3、Seek 3、Play 0。随后 Seek 200 秒，日志准备约 195 ms。

第 5 项前两首的不同准备时间不能直接归因于改进；缓存热度、源和宿主状态不同。日志时间不是端到端首声测量。第 6 项是一次样本，不证明全部歌曲、客户端和网络条件都无副作用。

## 部分文件范围处理

原生文件可能只写了开头，HTTP 本地挂载返回 `Content-Range` 的总长度是当前物理长度。仅对已由原生索引确认的本地范围允许总长度介于请求末尾和最终音源大小之间；区间起止、状态 206、实际字节长度仍严格检查。普通网络请求继续要求总长度精确等于源长度，未放宽网络校验。不能从物理文件长度推导有效区间。

## 打包和隔离

```powershell
python windows/package.py --native-source-trial --diagnostics
```

生成 `dist/gapless-player-windows-0.4.5-native-source-trial.plugin`。manifest 明确标为未完成验收的试验；不与 probe 或临时交还模式混用。不带开关打包仍采用原有数据源；本轮没有提升正式版本号。检查采用修改文件 Node 语法和 ZIP 打包，无常驻测试及全量构建。

本机试验期间使用同一插件 slug，正式包移到实验备份目录；结束后恢复正式 0.4.5 并正常重启。源码功能通过构建标志隔离，不把临时运行时补丁当成最终包验收。本轮最后对抢占错误的分类修正仅完成语法/打包，需随下一轮完整运行验证。

## 仍未达到发布条件

- 真实双曲首次衔接及曲尾跳转后的音频回录；主线程压力、弱网和连续切换。
- 实际清理原生磁盘缓存期间，读文件、Stop 提交及原生清理的顺序/文件锁验收。当前只是同步发送 Stop 并阻断旧 JS 任务，尚未证明原生磁盘写入已全部排空。
- 原生固定初始 0.221/0.266 秒计时的解释及统计上报隔离。
- 全进程音频请求审计；源码没有 Web 音频 URL 路径，不等于已排除所有原生后台重复下载。
- 冷源起播门限：试验允许最多八秒失败等待，仅为研究边界，不符合最终尽量对齐原生起播的验收目标。
- PCM 整曲分配仍存在；Worklet/有界 PCM 输出与 Mac 原生适配仍未完成。

因此本轮是原生取数、原生整首缓存与 Web 输出集成的可运行原型，不能宣称全部最佳实践及跨平台原生体验已实现。
