# 无缝播放与原生行为对齐：调研及实施方案

日期：2026-11-15。调查基线：提交 `3a26e0a`，Windows 0.4.5 源码；Windows 网易云 3.1.43.205627 的既有实测。Mac 0.2.5 为未实机验收候选，Mac 原生证据来自仓库此前的独立调查。本轮重新审阅实现、实验记录及公开规范，没有重启客户端、删除缓存或部署新播放器。

## 结论与决策

用户目标是一个无缝开关，其他体验尽可能保持原生。最佳架构的排序应按职责保留程度，而不是按实现语言：

1. **原生取数、缓存、解码、连续输出。** 最符合目标；前提是能安全使用原生独立准备和跨曲提交能力。目前没有端到端通过的实现，不能把它列为现成选项。
2. **原生取数和缓存，Web 解码及连续输出。** 建议优先做有边界的 Windows 原型。已有目标区块读出实证，但实时有效区间、实例调度和状态隔离仍是上线阻断项。
3. **Web 自行取数、解码和输出。** 当前稳定版本的主要路线；可以流式播放和无缝，但无法声称原生磁盘缓存行为完整保留。保留作现有实现及明确的失败恢复选择，不以此宣布完成用户目标。

不推荐重新采用曲尾临时接管、曲头再交还：它增加两个输出时钟之间的对齐、设备延迟和音效差异，先前已经出现过交还卡顿。也不以静音播放另一条完整歌曲来维持缓存：这可能重复解码、下载、累计听音时间。

这是一份调查与实施契约，不是“所有行为已经对齐”的声明。原生私有音效、设备独占输出、特殊加密源等若不能保留，必须走原生；不能悄悄关闭这些功能来维持 Web 所有权。

## 一、证据及当前差距

| 事项 | 当前证据 | 判断 |
|---|---|---|
| Windows 原生纯无缝 | 有 Load/Play/Seek/preLoad；独立 preLoad 的两次既有短测未取得有效下一首数据；尚无跨曲原生回录 | 未证明可用，也未证明底层不能实现 |
| Mac 原生纯无缝 | 静态调查发现有条件复用输出；现有 SDK/宿主未接通，主进程访问探针未取得控制端口 | 有技术依据，尚未进入播放原型；不能套用到 Windows |
| Windows 原生作数据源 | Load+Seek 期间未发 Play；中间 230452 字节、末尾 155104 字节与授权源一致；末尾解码 88064 采样/声道正确 | 核心链路可行，非生产完整性证明 |
| 原生正常缓存 | 播放及暂停期间 .uc 增长，正常退出后出现完整索引；另一 Seek 样本仍有区间缺口 | 不是“曲终才统一写入”；不能凭文件长度判断有效数据 |
| 现有缓存读取 | `windows/native-cache.js` 仅接受 cached=100，并核对源元数据 | 完整缓存优先，部分缓存未复用 |
| 现有网络和内存 | 64 MiB 编码区间缓存；索引 FLAC 范围读取；PCM 仍按整曲分配，共享预算限制 | 已能边读边播，但不是有界时间窗 PCM 架构 |
| 现有输出 | `windows/streaming.js` 将已解码片段复制为独立节点，按同一时钟预约；完整后预约剩余内容 | 不依赖修改已启动节点的 AudioBuffer；仍依赖主线程及时补充预约 |
| 本地文件 | `windows/source.js` 经宿主 readFile 得到 Blob，后续 Blob.slice 读取 | 不能仅凭 slice 证明底层没有先读完整文件；需要查宿主实现及实际 I/O |
| 清理 | clearCache/onclearcache 联动插件内存；当前工作 PCM 保留 | 协议与内存验证已有，实际磁盘删除端到端未做 |
| Mac 对齐 | 尚未接入 Windows 同等流式路径；已有系统进度回跳问题 | 不能称两端完全一致 |

本地依据：[原生缓存原型](NATIVE_CACHE_PROVIDER_FEASIBILITY.md)、[结构化实验](verification/native-cache-provider-feasibility.json)、[缓存所有权](NATIVE_CACHE_OWNERSHIP_AUDIT.md)、[Mac 原生分支](NATIVE_GAPLESS_RECHECK_2026-11-15.md)、[Mac 接入结果](NATIVE_GAPLESS_ATTEMPT_2026-11-15.md)、[0.4.5 清理](WINDOWS_CACHE_LIFECYCLE_0.4.5.md)。这些是既有实验，本轮没有重复音频验收。

## 二、原生路线应该怎样研究

真正无缝不是“网络提前加载完成”，而是有效 PCM 在同一输出时间线上连续提交。JS 收到 End 后再 Load/Play 不能提供采样级保证；两个独立播放器同时启动也不等于连续输出。

Windows 下一步先追踪实际客户端原生 preload 请求、准备完成事件、当前/下一实例身份、输出生命周期。要求查明以下能力：

1. 当前继续播放时，独立准备下一首的 provider/decoder，不替换当前流。
2. 在当前有效采样用尽前，将下一首提交给同一输出队列；格式不兼容则正常切换。
3. 管理器接认已准备实例，不再次 Load 造成输出重建；队列、曲名和听音统计只前进一次。
4. 暂停、Seek、切歌、设备更换能取消旧预约，并恢复正确的最新用户意图。

如果 JS SDK 没有这些能力，下一层才是版本绑定的受限原生桥。先验证宿主能加载到实际拥有音频对象的进程，以及 ABI、线程和生命周期，再做调用。二进制中出现 preload 类名不算可用接口；不把 Mac 类名、固定地址或权限结论复制到 Windows。

Mac 的既有 `prepareToPlay` 会切换共享当前流，不能拿它当后台预加载。应继续寻找真正独立的 provider/decoder 准备与流提交，并解决宿主原生入口；仅强制 gapless 标志不能保证格式安全。

成功标准是“原生同一输出 + 两首连续 PCM + 原生 UI/统计一致”的联合证据，不是设置命令成功或听感一次通过。无法证明时保持该路线未完成，不推导“只能 Web”。

## 三、Web 路线的职责边界

建议结构：

```text
网易云授权、用户音质、队列、原有界面
                 ↓
平台适配器：原生数据源和缓存有效区间
                 ↓
有界编码区块 → 增量解码 → 有界 PCM 区块
                                 ↓
                  唯一 Web 音频时钟及连续输出
                                 ↓
                 平台适配器同步进度、歌词、系统控制
```

设计接口（不是已发现的网易云 API）：`open(authorizedSource)`、`ensure(samplePosition, ahead, revision)`、`readReady(byteRange)`、`cancel(revision)`、`release()`；返回的每段数据携带源身份、有效范围、缓存代次。原生端只负责数据，不发布第二份可听输出或曲目信息。

Windows Load+Seek 仅是这个接口的候选实现：仍占用原生引擎实例，初始 playedTime=0.221/playedAudioTime=0.266 的原因未完全解释，不能宣称没有解码或统计成本。优先寻找真正独立的数据源入口；若只能用单实例，必须先保住当前曲尾 PCM，再切换实例准备下一首。用户此时往回 Seek，应撤销候选并优先恢复当前曲数据，不允许争用同一实例。

若无法可靠识别实时可读区间，不能把试验做成默认功能。文件大小、onBuffering=0、旧 .idx 都不足以独立证明任意范围有效；帧 CRC/解码成功可作校验，但不能替代下载完成的权威范围状态。需要原生范围通知、可验证的实时索引，或受限原生读取桥。

### 输出与启动

W3C 对网络/磁盘流的采样精确播放推荐 AudioWorklet；它解决输出线程连续消费，不负责下载或自动共享网易云缓存。[Web Audio 规范](https://www.w3.org/TR/webaudio-1.0/#AudioBufferSourceNode)

长期优先方案是解码任务向有界 PCM 队列供数，AudioWorklet 只消费、切换曲目边界并报告采样计数。音频线程不做网络、磁盘、同步 RPC 或大块内存分配；欠载报告真实缓冲状态，不把填零算成正常播放。

必须先验证当前 CEF、协议、安全上下文和 CSP 能按现有策略加载 Worklet/Worker。SharedArrayBuffer 还需额外能力条件，不能假定存在；可评估 MessagePort 可转移块并做时延/内存测试。不得修改宿主安全策略。能力不足时，采用已就绪的不可变小 AudioBuffer 提前预约，并在压力测试后确定预约水位；不能依赖边播边修改已启动节点的缓冲。[缓冲内容获取语义](https://www.w3.org/TR/webaudio-1.0/#acquire-the-content)

启动时安装命令桥、读取开关、准备解码模块；不播放静音曲目。音源规格尚未知时不强制创建固定采样率时钟，以免第一首发生重建或隐式重采样。拿到授权源和规格后可准备上下文；恢复须遵守用户播放意图和宿主自动播放限制。首次出声只等目标位置的小段安全缓冲，不等整首、不等下一首。

当前 0.75 秒首缓冲、8 秒前看、低于 4 秒补充等是实现参数，不是通用最佳值。应按实测解码吞吐、请求尾延迟、设备延迟调整并设上限。网络供数低于播放消耗时任何实现都不能保证无间隔。

## 四、四类数据来源与统一缓存

| 数据状态 | 目标行为 | 不应发生 |
|---|---|---|
| 用户本地文件/已下载文件 | 沿用宿主原来的本地源选择，按范围读取、定位、解码 | 同名匹配成在线版本；自动重新下载；清播放缓存删除用户下载 |
| 完整原生播放缓存 | 按权限和音源身份核验后直接读；重新启动仍可复用 | 再请求音频正文；把元数据/授权请求算成音频重复下载 |
| 部分原生缓存 | 读取已确认区间，原生只为缺口准备数据 | 把稀疏文件空洞读成静音；忽略全部已有区块 |
| 无缓存在线歌曲 | 原生按原有策略准备所需区间，Web 消费可读数据 | Web 和原生独立下载同一区间；额外强制整曲补齐 |

本地“未缓存”文件与在线“未缓存”歌曲不同：前者已有完整文件，缺的是解码内存；后者需要网络。缺失本地文件、加密下载、CUE/特殊格式由原生处理，不能自行用在线同名歌曲代替。

统一的是源身份、请求合并及持久化所有权，不要求磁盘压缩数据和内存 PCM 变成同一种缓存。源键至少区分账号/授权范围、曲目、实际质量、内容哈希或可靠版本、长度；本地还需文件修改/替换检测。URL 更新不必使同内容失效，但内容身份不能确认时禁止拼接。

只有原生写歌曲磁盘缓存及索引、执行配额淘汰；插件不自建永久音乐库，也不伪造 .uc/.idx/.info。按原生实际策略继续下载/提交元数据，不自行规定曲终或退出时机。播放结束不保证整曲完整：例如直接跳到末尾，前中段可能根本没有请求。

清缓存需要一个代次屏障：先取消旧预取和未提交读任务，转发原生清理，再丢弃挂载、区间表、闲置编码数据及 PCM；迟到响应不能重新填入旧代次。当前播放必需的缓冲可保留至安全边界，清理结果应区分磁盘缓存与工作内存。清理失败仍如实反映原生结果；恢复播放后新产生的缓存属于新请求。播放状态下文件句柄是否阻碍 Windows 删除，必须实测。

## 五、任意位置起播和拖动

统一流程：最新用户位置 → 源身份/代次 → 定位目标采样 → 查 PCM/编码/原生磁盘有效区间 → 为缺口准备数据 → 解码到准确目标 → 提交播放。首次恢复到中间、拖到末尾、末尾跳回中间采用相同流程。

FLAC 有 SEEKTABLE 时，从目标之前的可用帧起点读，解码并丢弃目标之前采样；字节偏移不是时间按比例换算。无表时可以查帧头、做有界定位或交给原生定位，不能宣称一定快速，也不能声称必须下载完整文件。[RFC 9639 §8.5](https://www.rfc-editor.org/rfc/rfc9639.html#section-8.5)

目标 PCM 已有则立即安排切换；只有编码数据则先解码；部分/无缓存则只请求目标解码所需范围及适度前看。连续 Seek 使用递增 revision，旧请求允许缓存已验证字节，但不得启动旧位置或回写旧进度。暂停时 Seek 仍保持暂停，恢复时从目标播放。

“等待时继续旧位置还是停声显示缓冲”必须以同版本原生实测为准，不能把目前继续旧位置的策略直接称作一致。UI 区分请求位置与实际播放位置；成功后从准确目标报进度，不套用 1–3 秒固定偏移。缓冲状态不应把累计听音时间算进去。

拖到曲尾不关闭无缝能力。目标曲尾缓冲就绪后，同时按剩余时间准备下一首；两者及时就绪才能无缝。如果只剩 100 ms 而网络还需 1 s，无法保证连续，应如实缓冲/正常切换，不能跳过尾音、提前播放下一首或降音质来掩盖。

MP3/AAC 等有编码延迟、尾部填充及容器索引问题，需格式专属有效采样处理；不能用删除静音代替。尚未适配的格式保留原生行为并标为无缝覆盖缺口。

## 六、网络调度与错误处理

主路径由原生拥有请求，插件只发目标位置和优先级。Web 直连仅在明确选定的替代模式使用；同一源不能同时有两个独立下载所有者。切换所有者需取消、复核区间和权限，不能为强求无缝反复抢占。

Web 请求实现须验证 HTTP 206、Content-Range、实际长度、源版本；服务端返回 200 不能当目标区间，416 要重新核对长度/版本。适用时使用可靠验证器及 If-Range，授权过期由原生重新解析，不降档。重试有界且可取消，范围合并/订阅去重避免多个消费者重复取数。[RFC 9110 范围语义](https://www.rfc-editor.org/rfc/rfc9110.html#name-range)

优先级：当前欠载/用户 Seek > 当前持续供数 > 临近曲尾的可信下一首 > 可选历史。下一首预取是首次无缝的必要准备，不能完全取消；但不需要为了预取全下载下一首。缓存命中后只补缺口。断网且目标区间已齐应可播放；未齐应沿用原生错误/缓冲体验，不伪装成功。

## 七、体验和功能逐项对齐

| 领域 | 对齐契约 | 尚需实测 |
|---|---|---|
| 播放/暂停/手动切歌 | 最新意图优先，新歌从 0 或明确恢复点开始；不因下一首准备拖延首曲 | 冷启动、热缓存、快速连续操作的延迟分布 |
| 自然切歌 | 同规格有效 PCM 连续、队列只推进一次；不裁剪作品留白 | 首次冷源、跳到曲尾后的真实输出 |
| 歌词/进度/动画 | 单一实际音频时钟，显示延迟与设备输出校准 | 主界面、详细歌词、迷你窗、桌面歌词 |
| 系统媒体/统计 | 一个控制目标和发布者；暂停、Seek 不虚增听音时间 | 媒体键、锁屏、SMTC/NowPlaying、上报次数 |
| 音量/音质/音效 | 保留用户原设置；相同音源不等于整条输出链相同 | 响度、峰值、采样率、设备模式、原生专属处理 |
| 生命周期 | 休眠/恢复、设备更换、刷新、关开插件均复核代次 | 无双声、无旧曲恢复、无残留挂钩 |
| UI | 一个顶部入口及开关，复用宿主控件 | DPI/主题/关闭按钮；不增加歌词页布局 |

相同采样率只是必要条件之一，还要核对声道布局、有效采样范围和输出策略。音质验收区分解码 PCM 一致与系统/DAC 输出一致；目前只在特定源验证过 PCM，不能承诺全场景 bit-perfect。

## 八、实施顺序与验收门槛

1. **原生基线与能力探针。** 同客户端、同音源、同设备，记录关闭插件时首次起播、各类 Seek、缓存增长/清理、正常退出和下一次读取；同时验证原生跨曲入口。先做只读采集，实际清理使用专门生成且可识别的测试缓存，不直接清用户全部缓存。
2. **数据源原型。** Windows 单曲原生取数＋Web 消费：冷启动无需先原生放歌；随机 Seek、中途暂停、连续供数均通过；取得可靠实时区间，证明无重复音频下载及统计副作用。未通过不进入下一阶段。
3. **两曲与输出原型。** 验证单实例切换或独立预取；采用有界 PCM，先查 Worklet 能力，不能用则分块提前预约。首次两曲、曲尾 Seek、快速返回当前曲都须通过。
4. **原生缓存生命周期。** 完整/部分缓存、退出重启、断网复用、账号/质量变化、清缓存时活动读取。确认磁盘目录和清理由原生统一拥有。
5. **功能对照与发布决策。** 以下矩阵通过才替换日常版本；Mac 单独适配验收，不从 Windows 结果直接发布。纯原生若先通过完整门槛则优先选它，Web 可保留为显式兼容后端。

| 场景 | 验收证据与判定 |
|---|---|
| 空缓存第一次播放和连续两首 | 请求时序、首声时延、解码队列及回录；不等整曲、无第二轮才生效要求 |
| 完整缓存重启后再播放 | 音频正文网络请求为零；允许原生原有授权/元数据请求 |
| 部分缓存从尾部再回中间 | 已有效范围复用、缺口才取数、位置精确；无文件空洞当 PCM |
| 本地文件 | 不请求在线音频；读取内存和磁盘 I/O 有界；路径替换可失效 |
| 自然边界与尾部 Seek | 同源参考 PCM 联合回录，无新增零段、重复/丢失采样；用交叉相关校准系统录音延迟 |
| 快速切歌/拖动/暂停 | 最后意图胜出；未提交旧操作不会出声或更新 UI |
| 网络断开、Range 异常、权限变化 | 有限重试、正确缓冲/恢复，不降档，不错拼版本 |
| 清缓存、退出和重启 | 实际文件/索引及请求审计；清理代次后无旧任务补写；用户下载保持 |
| 线程压力及长播放 | 欠载计数、实际声音连续性、峰值内存/CPU；分块内存稳定，不随曲长增长 |
| 系统控制及音效 | 与原生基线对照状态、统计、音量/音效；不兼容路径明确且恢复正常 |

起播/Seek 用同条件多次测试报告中位数和尾部延迟，并拆分授权、取数、解码、输出等待，不能用单次日志宣称更快。上线阈值在原生基线采集后固定；无缝采样边界标准不因性能取舍而放宽。音频链与网络/文件链都要记录：仅插件 fetch 日志不能排除整个进程重复下载。
