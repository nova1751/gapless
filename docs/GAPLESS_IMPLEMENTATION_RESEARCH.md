# 无缝播放技术路线调研

日期：2026-11-14。审查对象为已安装的 Mac 0.1.4；网易云 3.1.12（3444）。本次对照源码、上游播放器设计和标准文档，并完成运行中 SDK 的只读检查及本机原生二进制静态检查；没有改变播放代码、安装包、客户端设置或暂停意图，没有完成新的声卡回录。原生检查证据及 Windows 对照见 [原生可行性实查](NATIVE_GAPLESS_FEASIBILITY.md)。以下架构建议尚未实现。

## 判断

同一 AudioContext 中提前预约 AudioBufferSourceNode 是正规的音频调度方案。当前实现比较 hack 的部分是网易云接入：读取 React/Redux 私有结构、扫描压缩后的 Webpack 模块、包装 Mac 通信入口、屏蔽原生事件并代发播放器状态，以及在歌曲播放中途从原生后端切换到 Web Audio。

当前方案适合作为有明确版本和规格限制的插件实现，不能认定为副作用最小的最终架构。对“音质和其他原生特性优先，只增加无缝”的要求，优先寻找可验证的原生队列预准备能力；缺少该能力时，自建后端仍需要接管播放及同步原生状态，无法仅靠一次预加载调用达到同样效果。

## 成熟引擎的做法

GStreamer 的设计是在上一首结束前准备下一条解码管线，跨曲时保留输出链；其 streamsynchronizer 文档同时要求提前缓冲、准确处理有效采样边界、不因切歌暂停管线，以及避免重置音频设备。[GStreamer 无缝切换设计](https://gstreamer.freedesktop.org/documentation/additional/design/playback-gapless.html)、[无缝播放条件](https://gstreamer.freedesktop.org/documentation/playback/streamsynchronizer.html)

目标是让上一首的最后一个有效采样帧后紧接下一首的第一个有效帧，界面更新不阻塞音频消费。下一首由权威播放队列决定，网络和解码在音频回调之外完成，输出端持续消费有界缓冲。这是架构方向，不代表网易云当前已提供这些接口。

```mermaid
flowchart LR
    Q[播放器确认下一首] --> D[提前获取与解码]
    D --> B[当前尾部 / 下一首头部缓冲]
    B --> O[持续运行的输出时钟与设备]
    O --> U[播放进度与曲目事件更新 UI]
```

跨规格还需要明确取舍。mpv 的 gapless-audio=yes 保持最初输出格式，后续文件可能转换采样率；weak 在格式不兼容时允许重开设备，因而不保证该边界无缝。保持原生规格与任何规格之间绝对零间隔，不能同时无条件承诺。[mpv gapless-audio](https://mpv.io/manual/stable/#options-gapless-audio)

编码器 priming/padding 是无缝播放本身的正确性问题。Apple 的压缩音频循环说明和 FFmpeg 的 SKIP_SAMPLES 定义都区分开头延迟、结尾填充和有效音频；按可靠元数据排除编码附加帧，属于恢复有效音频范围。它与按波形裁掉歌曲留白、交叉淡化或响度调整不同。[Apple QA1636](https://developer.apple.com/library/archive/qa/qa1636/_index.html)、[FFmpeg 包附加采样信息](https://www.ffmpeg.org/doxygen/7.1/group__lavc__packet__side__data.html)

当前 MP3 没有实现显式元数据边界处理，但不能因此断言每个文件都有填充残留：具体 Chromium 解码器可能已经处理一部分元数据。须先比较已知有效帧数、编码元数据与实际解码结果，再决定是否补偿；重复应用延迟/填充会截掉音乐。FLAC 同样应核对 STREAMINFO 的有效帧数，不能用文件名或普通时长近似替代。

## 路线对比

| 路线 | 对本需求的价值 | 代价与前提 | 判断 |
|---|---|---|---|
| 网易云原生引擎提前准备下一首，并继续使用原输出链 | 最有机会保留原生解码、音效、设备及统计语义 | Mac 3.1.12 底层存在跨曲逻辑，但已检查 SDK 的预加载方法为空实现，未找到可验证的调用路径；Windows 须单独实查 | 首选架构；本轮不能安全落地 |
| 当前完整解码缓冲 + Web Audio 预约 | 调度核心较简单，同规格缓存就绪后可提前预约 | 完整获取、较高内存、歌曲中途后端交接、私有状态同步 | 可继续维护，但明确是受限插件方案 |
| 持续流式解码 + 有界 PCM 队列 + AudioWorklet，或独立原生引擎 | 有机会降低完整解码内存，从曲目开始即使用同一后端 | 新增解复用/解码、背压、Seek、欠载恢复和平台适配；仍改变原生输出链 | 只有资源瓶颈和平台能力得到证实后再考虑 |

W3C 明确将 AudioBufferSourceNode 用于内存音频的准确调度，并建议需要网络/磁盘音频逐采样调度时使用 AudioWorkletNode。它也明确 decodeAudioData 会向解码上下文采样率转换，输出上下文与设备采样率不同时仍要转换；指定源采样率不能证明最终设备输出与原生相同。[Web Audio 推荐标准](https://www.w3.org/TR/2021/REC-webaudio-20210617/#AudioBufferSourceNode)

Worklet 不是下载器或文件解码器，单独替换节点不会获得流式播放，也不会消除原生与 Web Audio 的交接。可以让 Worker 准备 PCM、由 Worklet 消费有界队列，但必须验证当前客户端的 Worklet、解码格式和共享内存能力；不能沿用旧示例的实验性开关要求。音频回调不可等待网络或重计算，欠载和超时仍会卡顿。[Chrome 音频线程设计](https://developer.chrome.com/blog/audio-worklet-design-pattern/)

## 当前源码中的具体缺口

| 位置 | 已确认的做法 | 影响 |
|---|---|---|
| mac/player.js:18–64 | 从 React 私有节点找 store；扫描 Webpack factory 字符串定位签名请求；固定版本能力检查 | 网易云升级、压缩和模块组织变化可导致失效；版本回退保护必要 |
| mac/startup.js；mac/player.js:389–455 | 包装原生通信/回调，屏蔽部分事件，代发 Load/进度/播放状态 | UI 和声音由不同状态来源驱动；需处理旧命令、Seek、暂停、接认失败等竞态 |
| mac/player.js:248–277 | 播放中暂停原生，再从推算进度用 Web Audio 续播，起播安排在 contextTime + 10 ms | 暂停通知、UI 推算位置与原生最后一个可听采样不是同一测量；输出预热不能证明此次交接无缺失或重复帧 |
| shared/audio-resources.js | 完整下载和解码当前/下一首；512 MiB 管理预算，128 MiB 单文件限制 | 额外流量、内存及解码/复制开销；预算不包括 Chromium 和设备的全部峰值 |
| mac/player.js:134、603–638 | 每次 store 更新和 150 ms 心跳重复计算队列签名，调用候选查询 | 可减少的主线程扫描/分配；不是逐帧声音卡顿的已证实唯一原因 |
| mac/player.js 的 getPlaybackInfo 路径 | 不伪造返回值，交给原有 SDK；本轮确认该 Mac SDK 方法直接返回空对象，并未调用原生 | 无法用此方法测量当前设备或两个后端的状态；原先“由暂停后端回答”的描述不准确 |

0.1.4 已把输出冷启动等待移到原生仍播放的阶段，修正方向合理。但跨曲附近仍记录到 124–128 ms 的 UI 长任务，归因尚未完全确定；600 ms Web Audio 渲染窗口无静音不能替代设备输出验证。[现有卡顿记录](HANDOFF_HITCH_REVIEW.md)

## 对本仓库的建议顺序

1. **先确认原生能力。** 分别在目标 Mac/Windows 客户端识别是否有不推进 UI 的下一首准备、排队、无缝模式或稳定音频管线接口。先观察已发生的调用，再验证队列及控制语义；不向未知接口盲发播放命令。BetterNCM 的公开契约主要描述注入和宿主模块，不是网易云官方无缝音频 API。没有找到接口不等于证明底层不存在。[宿主契约](https://github.com/OyangDer/betterncm-mac/blob/main/CONTRACT.md)
2. **先减掉能确定的额外开销。** 根据队列身份/版本缓存下一首和签名；只在有关字段变化时重算。心跳承担进度和漏事件校正，避免完整队列扫描。关闭插件时保留必要的原生放行和恢复，尽量停止不必要轮询。必须保留队列变更取消和边界控制保护。
3. **单独解决首次后端交接。** 先回录实际设备输出，与解码参考对齐，区分首次交接、已预约边界及原生恢复。若必须使用独立后端，长期目标是在曲目开始前选好后端，并在连续曲目中保持同一输出，而非歌曲中途反复切换。完整解码会延迟首次起播；流式解码增加实现成本。简单把交接移到切歌点或禁止临近末尾接管，不能保证首次边界无缝，且可能重现无缝失效。
4. **确认并补齐有效帧边界。** 用可核对的 MP3/FLAC 元数据和已知素材确认解码器行为，避免二次裁剪。处理编码附加帧属于目标功能；保留作品留白，继续不加入混音、自动入点和音色处理。
5. **按测量决定是否迁移流式引擎。** 只有完整解码造成的真实峰值/CPU/起播时间构成主要瓶颈，才值得引入 Worker/Worklet 或原生库。它不会自然解决私有 UI 协议和原生特性一致性，不能因技术更复杂就认定更可靠。

控制代次、取消、源指纹、单次 End、原生恢复和资源限额属于接管播放器所需的保护。当前应减少重复工作和跨后端切换，而不是删掉这些保护。Mac 与 Windows 应共享控制语义和有效帧处理，平台只承担协议差异；Windows 当前仍没有本仓库的可运行实现。

## 验收依据

预约参数差为零只证明计划相同。至少区分首次原生交接、两首已预约的边界、恢复原生三类场景；用已知连续素材回录设备或数字环回，对齐参考信号，检查新增静音、缺失帧、重复帧、边界突变及音量变化。保留素材原有静音，不能只用“没有零值”判定通过。

再覆盖拖动后立刻暂停、连续拖动、边界手动选曲、大队列、后台/前台和设备变化，并记录 UI 长任务、内存峰值、下载字节及输出中断。此处是后续手动验收要求，本轮没有新增测试用例或声卡采集。

对本需求的最终取舍：原生能力可验证时优先复用原生音频链；能力不可用时，保留清楚标注的替代后端方案和规格边界，通过实际输出测量降低风险，不宣称其他原生特性完全等价。
