# Windows 0.4.3：优先准备跳转区块

## 行为

0.4.2 拖到未解码位置仍等待从头顺序解码。0.4.3 对有有效 SEEKTABLE 的受支持 FLAC，从目标之前最近的索引点按字节范围读取，只解码目标附近区块，并继续准备后面的区块。原位置保持播放，目标及之后约 0.5 秒就绪后，在同一音频时刻停止旧节点、开始目标节点；不加交叉淡化，不裁剪静音，不切换音源。

区块直接填入现有 PCM 缓冲的绝对采样位置。调度器区分连续已解码前缀与稀疏就绪区间，不把中间空洞作为可播放 PCM，也不把部分就绪误报为整曲完成。新 Seek、Stop、关闭及恢复会撤销旧范围请求；暂停期间允许准备，但不得擅自恢复播放。

下一首不再被当前曲的整首解码阻塞：Windows 首段 PCM 发布后即可开始下一个已授权资源任务；继续遵守共享内存预算、源身份与 retain 取消规则。Mac 未启用此策略。

## 来源与校验

- 已命中网易云完整缓存时，仍从同一缓存文件按范围读取，按已有 XOR 格式还原，不改写缓存。
- 网络仅请求当前授权 URL，要求精确 HTTP 206 / Content-Range / 文件大小 / 区块长度；拒绝把返回整文件的 200 当成范围响应。单次范围读取最多 10 秒。
- 本地文件使用已打开 Blob 的 slice；宿主 openLocal 仍可能先读取完整文件，不宣称本地文件系统随机 I/O 已优化。
- 索引按 [FLAC 标准](https://www.rfc-editor.org/rfc/rfc9639.html#section-8.5)解析，不按时间比例猜测字节位置。检查首帧编码位置、解码样本数、采样率、位深、声道及解码错误，沿用既有整数到浮点转换。解码器接口依据[官方说明](https://github.com/eshaz/wasm-audio-decoders/blob/main/src/flac/README.md)。
- 每个区块最多 2 MiB 编码数据、4 MiB 临时 PCM；范围任务占用 8 MiB 预算并固定引用当前缓冲，结束释放。索引必须完整落在首次头部数据中，超出、缺失或异常时不使用快速路径。
- 缓存完整 MD5 仍由顺序读取任务结束时验证。只读了部分区块，或换曲取消整首读取时，不能声称已验证整文件 MD5；范围路径使用授权元数据、索引位置、解码规格和帧错误检查。

## 实测（Windows 3.1.43.205627 / BetterNCM 1.3.4）

- Baptized In Fear 冷启动刚起播即拖到 229.176 秒：最终候选目标就绪等待 142 ms；此前 0.4.2 顺序等待的一次记录为 3642 ms。不是统计基准。
- 命中 native-cache，目标第一区块 75 ms 就绪；后续尾部区块继续读取。旧节点与新节点预约同一交接时刻（60 ms 提前量，不是插入 60 ms 静音）。
- Open Hearts 在曲尾到达前约 2.419 秒完成预约，scheduledGapFrames=0；发生 boundary / claimed，未出现原生回退。claimed 的 427 ms 是宿主界面接认耗时，下一首音频早已按时钟排程，不是声学间隔。
- Open Hearts 授权网络源的尾部范围解码，与 Chromium 完整解码比较 434846 个声道采样值，差异 0；44.1 kHz / 16 bit。该样本验证不能推及所有音源、系统重采样或 DAC bit-perfect。
- 连续拖到 229、220 秒并立即暂停：两个请求均回复，仅完成后一次目标（251 ms），活动节点为零，未自动播放或恢复原生。
- 修改文件语法与 ZIP 打包检查；未新增常驻测试用例。本轮没有系统音频回录，以上为协议、调度与 PCM 验证。

## 边界

没有索引、范围请求不支持、预算不足或区块校验失败时，快速路径退出，Seek 保留 Web 模式并等待正常顺序缓冲，最多 10 秒后取消此次 Seek。网络断流、音源完整性错误等原有恢复保护仍可能触发；不保证弱网或任意歌曲即时跳转。

任意手动上一首/下一首仍受宿主 Stop→Load 事务间隔影响，本版解决的是拖动未解码位置及其后续曲尾衔接，不宣称消除了所有手动选曲间隔。界面及音质选择未变；Mac 仍需独立适配与实机验收。
