# 缓存、Seek 与后台补齐复核

2026-11-16，基于 `5123e10`。Mac 0.3.7 已更新安装；Windows 0.4.9 为源码候选，本轮未操作 Windows 机器。没有新增测试文件、全量静态检查或应用构建。使用 Node 18 增量语法检查、实际函数隔离运行、Mac 原生 SDK/IDX 观测和 ZIP/runtime 对照。[脱敏证据](verification/cache-seek-0.3.7-0.4.9.json)。

## 确认的缺陷与修正

| 范围 | 缺陷及影响 | 修正 |
|---|---|---|
| Mac native-source/read | 复用的 IDX 快照缺口已被后台补上，仍启动重复取数；并发写入导致文件属性变化时直接失败 | 缺口请求前刷新有效索引；文件变化仅重读一次，仍受原八秒期限与身份/区间校验约束，返回前复核取消及来源 |
| 两端 native-cache/snapshotSource | 第一份 IDX 不匹配或损坏直接终止，后面的有效目录/文件不再检查 | 拒绝并记录无效索引，继续查找有效候选；全部无效时返回未命中，由原生准备或原生回退。绝不按文件长度宣称有效 |
| Mac seekOwned/boundary | 曲尾等待未缓存 Seek 时，旧节点结束先触发 End，导致自动换曲、目标失效或保持停止 | 以当前 Seek 代次保护边界及预约，备妥后按请求播放意图重新启动目标；暂停/后续操作优先，旧请求不能清理新请求 |
| Windows native-byte-source | 前台抢占、队列清理把可重试的当前区间读取直接当作故障 | 未主动取消的请求重新核对来源、清理屏障和 IDX；八秒截止不变，主动取消不重试 |
| Windows maybeFill | 异步读索引期间前台 PCM 下降，旧的安全判断仍允许低优先级补齐 | 提交前再检查当前实例、连续六秒缓冲、Seek/加载/接认状态及来源身份；前台优先 |
| Windows Seek/recover | 普通 Seek 的真实取数失败只回复失败，或回退使用旧位置；已知 Range 故障仍可能等满十秒 | 当前真实故障携目标交还原生；源错误及时终止等待。替代/换曲不回退；恢复中新的 Seek、暂停优先，原生恢复确认成功后才回复成功 |
| Windows cacheClearRequested | 近期辅助 Stop 后，属性观察失败跳过最短等待，扩大延迟提交与删除竞态 | 失败时补足五百毫秒宽限；已超时不额外等待，无近期 Stop 不新增等待。仍转发清理并保持取数屏障 |

这些改动没有改变授权音源、FLAC PCM 转换、采样率、固定音量增益或曲间预约方式，也未新增辅助 Play、永久缓存、EQ 或淡化。

## 本轮证据

实际函数隔离对照：旧 Mac 曲尾 Seek 会发 End 并失去当前曲，修复后等待完成在目标 50 秒启动；暂停不启动，后续 80 秒请求不被旧请求覆盖。两端第一份错误大小的 IDX 被跳过，第二份有效索引只允许 `[0,50)`；全无效时无可读区间。Mac 旧快照重复批次、并发写入重读，Windows 抢占重试/主动取消、缓冲下降时禁止补齐、目标失败及恢复期间新控制均有对照。它们验证控制逻辑，不代表 Windows 实机或声卡验收。

Mac 首次 0.3.7 安装的缓存读取修正后：完整缓存歌曲四次暂停 Seek，SDK 就绪等待 179/57/12/8 ms，位置匹配，辅助批次增量零、读取六次、失败增量零，采样率 44.1 kHz。部分缓存歌曲 857905 跳到 189.07655 秒，SDK 目标就绪约 1024 ms；有效区间由 `[0,7125997)` 扩展到 `[0,7864320)` 和 `[20949116,24356138)`。这是 SDK/目标 PCM 就绪时间，不能当作实际首帧出声时间，也没有强制等待整首。

随后约八秒播放中，后台两次原生批次在 73.9788 秒位置未增加覆盖；共覆盖 11,271,342 / 24,356,138 字节，仍有中间缺口。记录中一次源失败属于下一首 724495 的索引身份错误，不是当前歌曲读取失败。该错误促使补修索引候选处理。

曲尾 Seek/无效索引补修后重新打包安装，manifest/player.js 与 release ZIP 逐字节一致，包 SHA256 为 `686e3879d3cb8dfe9675c110220f336bfe9ffe1556d83588ac06a4247b3f4a44`。保留原曲 864433778、1.455102 秒及暂停。窗口工具报告 `cgWindowNotFound`；最终重载等待真实用户激活，零活动声音节点，不能宣称最后补修后的声音/UI 已重新验收。旧 0.3.6 包在启用目录外保留用于回退。

## 仍然存在的边界

- **整首缓存是尽力补齐。** 原生暂停 Load→Seek→Stop 不保证请求位置后持续取数；稀疏 FLAC 索引的前置锚点可能落在已有缓存内。本次两批未推进，保留指数退避、连续六次无进展暂停、切歌后最多两首/十分钟的元数据期限。没有为了缓存启动第二路音乐，不能承诺跳尾后一定全曲落盘。不同源的既有整首提交及重启复用证据仍有效，但不能替代这个失败场景。
- 目标区间缺失仍需原生取数、提交、解码，可能等待；八秒取数/十秒 PCM 准备上限不是人为设置的切歌延迟。网络、原生提交、未验证格式失败仍交回原生。
- 五百毫秒宽限/稳定窗口只是减少已知清理竞态，不是原子提交或 flush 确认。极端延迟落盘仍可能超过窗口。
- 本轮没有新跨曲回录、冷源重启/清缓存操作、最后补修后的 UI 声音回归或 Windows 安装。macOS 控制中心进度外观回跳仍不能宣布修复。

## Windows 0.4.9 复验方案

沿用 [0.4.8 安装与场景方案](WINDOWS_REPAIR_PLAN_0.4.8.md)，产物版本改为 0.4.9。只在已适配客户端 ZIP 内生成包，启用目录保留一个 slug，旧包放目录外。

优先核对：完整缓存 Seek 不启动辅助批次；部分缓存跳尾只等目标有效区间；Seek 抢占下一首准备不被误判；等待中暂停/换曲后旧请求不出声；目标读取故障按最新位置/意图恢复原生，每个 SDK Seek 完成一次；前台缓冲下降时不提交补齐；近期 Stop 且属性读取失败后清理仍转发、屏障保持。分别记录 SDK 就绪、实际声音、IDX 覆盖与退出重启复用，不拿缓存百分比或文件长度替代有效区间。
