# 原生数据源试验：声音与清理验证

2026-11-15，Windows 网易云 3.1.43.205627，独立 native-source-trial 模式。实际音频只录 WASAPI 系统输出，没有使用麦克风。音频文件保存在本机实验目录，不提交仓库。

## 发现并修复的欠载

首次将 Baptized In Fear 拖到曲尾约五秒，准备好的首个 FLAC 区间只剩约 0.82 秒可播。原先 Seek 只要求目标后 0.5 秒 PCM，立即换到目标；后续原生 Load/Seek/Stop 和索引读取未及时完成，触发 stream-underrun 并交还原生。这次明确失败，不能把参数预约 0 帧间隔当作成功。

原生数据源的 Seek/恢复位置改为至少两秒连续 PCM（曲尾不足则到曲尾）；网络旧路径维持原阈值。扩大门限后发现首次起播只准备了约 1.997 秒，起点为零时旧逻辑不继续准备，因而等到十秒超时。已修正为任何流式起点都启动目标窗口准备，避免该等待死锁。

## 修复后一次双曲回录

重新启动试验包，第一次准备 Baptized In Fear 的日志约 1478 ms；拖到 227.176 秒后，准备约 546 ms，随后自然跨到 Open Hearts。边界日志及音频回录均覆盖切换；界面接认约 204 ms，不等于音频断开时间。

- WASAPI 48 kHz 双声道，30 秒回录，回调错误 0。
- 以本次实际解码的上一首尾部三秒和下一首开头三秒为参考，跨边界前后四段相关系数约 0.940–0.970。
- 校正固定输出延迟后，前后对齐误差跨度约 1.354 ms；边界前后 100 ms 内最长近零段 0 ms。
- 本次没有 stream-output-fallback、claim-timeout 或原生恢复事件。

[结构化分析](verification/windows-native-source-audio.json)。这是一次已缓存区间的曲尾 Seek 样本，不是冷源/弱网、任意设备或 DAC 采样级证明；线性重采样参考及系统回录也存在测量误差。最初失败回录与中途门限死锁记录均保留在本机，不被成功样本覆盖为“全部通过”。

## 原生清理实测与回调差异

1. 复制一首缓存的 .uc/.idx/.info 到专门测试目录，调用原生 clearCache 指定该目录。副本确实删除，原有三文件校验不变；但没有收到 onclearcache，直接 SDK 等待也超时。因此不能对任意路径都无限等待完成事件。
2. 默认当前缓存入口：先完整备份原缓存目录 27 文件、213541099 字节，再暂停状态调用原生 SDK clearCache()。约 457 ms 返回 true，收到 storage.onclearcache，目录文件全部清除，Web 所有权保留，当前工作 PCM 约 82.9 MB 仍保留。
3. 正常退出后检查，没有旧任务重新写回缓存。将 27 个原文件恢复，逐文件 SHA-256 与备份一致。没有永久删除用户缓存，也没有改动用户下载目录。

上述默认清理发生在暂停状态；不能直接外推到网络写入中的最激烈竞争。另一次 Stop 后 getPlayedTime 仍返回 result=true 和固定 0.221 秒，不能把它作为原生文件工作已全部排空的完成信号。

## 新增清理屏障

默认清理请求开始时，取消取数队列和后台补齐，并阻止新的原生取数；收到原生 onclearcache 后再允许请求。明确目录的旧缓存清理不等待本机未发出的事件。新读请求等待最多四秒，超时交回原生，不能在未确认清理结束时自行解除屏障并重新补写。

本轮最后新增的屏障已做修改文件语法及 ZIP 打包检查，尚未在真实活动下载场景验收。仍需验证屏障、冷源连续供数、统计、长期内存和全进程请求。当前安装在实验结束后恢复稳定 0.4.5，不将这次单边界成功当作正式发布批准。
