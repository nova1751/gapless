# Windows 0.4.2：拖动进度与手动切歌

## 已确认的问题

0.4.1 的实际操作日志出现 Seek 后 `stream-underrun`、原生恢复：目标位置尚未解码，播放器却立即从该处排程。回到原生后，自然曲间预约也随之失效。另一个问题是宿主 Stop 清理下一首预加载，手动选曲重复初始化输出和原生静音保护。

## 本轮修正

- 未解码位置的 Seek 等待目标及其后约 0.5 秒就绪，最多 10 秒；等待期间原位置继续播放。新 Seek、Stop、关闭和恢复撤销旧请求，暂停后不得自行恢复播放。
- Load 期间收到的 Seek 同样检查目标缓冲；不再把未填充 PCM 当成可播放内容。
- Stop 保留已授权、环境仍一致的下一首准备；只把完整、无错误的当前曲保留为最近播放缓存。
- 连续有效 Load 复用运行中的同规格输出时钟及原生静音保护。空闲清理仍释放保护，异常仍走恢复流程。
- 解码每约 4 ms 通过 MessageChannel 让出主线程，避免嵌套定时器延迟积累。未增加 Worker 或修改 CSP。

没有修改音源、音质档位、PCM 转换、窗口样式或增加插件。Mac 未改动，也没有本轮 Mac 实测。

## Windows 实测与限制

客户端 3.1.43.205627 / BetterNCM 1.3.4；使用“我喜欢的音乐”中的 Baptized In Fear 与 Open Hearts。

- 冷启动首曲刚出声后拖到最后约 3 秒：修正后等待目标就绪，保持 Web 输出，随后接认下一首；未出现此前的 stream-underrun / 原生恢复。优化让出机制前等待 7966 ms，本次优化后 3642 ms；这是两次观察，不是统计基准，首次拖到远处仍可能等数秒。
- 已准备的两首手动前后切换：内存命中，插件 Load 分别 6 / 8 ms，从零起播，复用同一上下文；暂停后活动节点归零。
- 单独跟踪手动选曲：旧歌 Stop 在 235 ms，新歌 Load 在 524 ms，Play 在 537 ms。Stop 时宿主仍选中旧歌，不能仅凭该消息可靠判断下一目标。**宿主 Stop→Load 的 289 ms 间隔仍存在，6 ms 只是插件 Load 耗时，不是端到端切歌耗时。**
- 连续请求 229 秒、220 秒后立即暂停：两个请求均收到回复，最后仅完成 220 秒目标（等待 3775 ms），仍由 Web 持有，活动节点为零，未自行恢复播放。
- 不延迟普通 Stop 来假装无缝，不越过网易云授权播放缓存候选，不用交叉淡化掩盖间隔。消除上述手动间隔需要在宿主选曲事务前识别目标、取得有效授权并验证取消/停止语义；本版未实现。
- 本轮为控制协议和运行日志验证，未新增系统音频回录。自然曲间零帧预约不等于任意手动选曲零等待，更不等于设备输出逐样本验收。

后续验收必须分别记录冷启动起播、未解码位置 Seek、热缓存手动切歌、自然播放边界；不得只测第二次播放便宣称首次也无缝。
