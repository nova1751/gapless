# 原生取数、Web 输出：可行性实测

## 结论

在 Windows 网易云 3.1.43.205627 上，已经验证出值得实现原型的路径：原生执行 Load、保持非持续播放状态，用 Seek 准备目标区块；Web 读取原生 .uc 的可用数据，解码并排程输出。磁盘数据及 .idx/.info 由原生写入，插件只读。

这不是已经找到独立、公开的下载服务接口，也不是已完成生产适配。仍会占用一个原生加载实例及其资源；原生内部是否执行短暂解码、统计如何隔离等还需处理。已安装版本保持 0.4.5，没有把试验路径自动用于日常播放。

## 四条路线的调查

1. **独立 preLoad：本次未成功取得可用数据。** 对此前没有有效磁盘缓存的下一首，通过 SDK 对应参数调用 audioplayer.preLoad，9 秒内 cached 一直为 0，未收到该实例加载事件，只产生 0 字节 .uc。另一次在原生冷启动并完成实际播放后调用，6 秒观察仍未获得下一首数据。这不证明接口永远无效，但不能据此交付独立缓存服务。
2. **orpheus://cache：当前不可用作歌曲数据源。** 本机代码将其用于图片/世界效果视频。授权音频范围请求实际被 CORS 拒绝，错误为 Access-Control-Allow-Origin 有重复的 `*, *` 值；CSP 中已经允许该协议，不是修改 CSP 能合理解决的问题。没有修改安全策略。即便修复响应头，此通道属于 HTTP 页面资源缓存，尚未证明会登记到歌曲缓存。
3. **原生正常播放对照：确认落盘。** 冷启动关闭插件后原生实际播放约 8 秒，getPlayedTime 验证有效；暂停后原生缓存继续增长。正常 app.exit 后，一首歌的 .uc 为 26511114 字节，.idx 为完整区间 `0 26511113`，并生成 .info。不能将播放期间 cached=0 或缺少 .idx 解释为原生没有写数据。此前使用强制结束进程的观察不能确定索引正常刷盘时机。
4. **原生 Load + Seek，Web 保持输出所有权：核心链路成功。** 对另一首未完整缓存的授权曲目创建独立 native playId，只发送 Load 和 Seek，不发送原生 Play；隔离该实例的 UI 通知。原生播放计数在观察期间保持 playedTime=0.221、playedAudioTime=0.266，并未持续增长。初始非零值的含义未完全确定，不能把它描述为原生完全没有解码或计时副作用。

## 成功路线的具体证据

- Seek 到 120 秒后，从原生 .uc 读取目标 FLAC 区块 230452 字节，XOR 还原后与同一授权源的相同区间逐字节比较，差异为 0。
- Seek 到 237.066 秒（距曲尾 4 秒）后，收到 onSeek 成功、onBuffering=1→0。原生缓存目标区块 155104 字节与授权源一致；Web 解码器解得 88064 个每声道采样，符合预期，44.1 kHz，解码错误 0。
- 两次 Seek 后原生 playedTime/playedAudioTime 未继续增长。测试中 Web 所有权保持开启；不是用两条持续播放的音频来制造效果。
- 通过 app.exit 正常关闭后，原生生成 .idx 和 .info。索引总大小 26684744，有效区间为 `0 6641683`、`13591884 26684743`。中间没有读取的部分仍是缺口；.uc 文件长度等于整曲大小并不代表所有区间都有效。
- 测试没有由插件写入 .uc/.idx/.info，也没有更改原生缓存配置或执行缓存删除。验证用网络范围请求仅用于对比原生文件字节，不是生产方案必须的第二次下载。

## 原型应如何实现

1. 原生缓存实例取得网易云已经授权的原音质音源，独占下载与磁盘缓存管理；保持非持续播放状态，Web 独占可听输出。
2. 首次起播或拖动，先给原生准备相应位置，等待可用性通知，再读取目标区块；读取不以文件长度为依据，必须检查数据完整性和对应的采样位置。
3. Web 正常播放时补充前方数据，手动跳转优先；不要为了缓存完整度强行下载未播放的缺口，也不要模拟“歌曲结束后才写入”的固定时机。
4. 原生自行登记、落盘和清理。完整或已确认的部分缓存供下次复用；插件只保留有界的解码缓冲，不维护第二套永久音乐库。

## 进入日常版本前的门槛

- 验证 native Load→Seek 在不同起播/暂停/恢复状态下的资源生命周期，不依赖试验前运行过原生播放器。
- 建立可靠的实时可读区间协议。.idx 可能延迟生成，onBuffering 完成只证明播放器缓冲条件满足，不足以证明任意请求字节区间都完整；不能读取稀疏文件空洞当音频。
- 连续播放推进原生取数窗口，同时避免额外播放时长、听歌统计、歌词/系统媒体状态回写。
- 同一原生实例准备下一首时，需要保住当前曲尾的 Web 缓冲，验证当前/候选的取消和源身份。独立 preLoad 未通过，不能直接假定它解决多曲准备。
- 原生清缓存、断网、音源过期、快速拖动、用户退出时要取消读操作并正常释放/提交原生状态。
- 评估原生加载实例带来的额外解码和内存成本，最后进行音频回录和持续播放验收。
