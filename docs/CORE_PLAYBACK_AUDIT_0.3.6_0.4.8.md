# Mac 0.3.6 / Windows 0.4.8 主要播放路径检查

2026-11-16，基于 main `62da6e5`。检查播放接管、同率预约、Seek/恢复、原生回退、候选错误归属、音量、缓存和开关；不是全客户端或所有音源的完整验收。第一阶段仅修源码；随后按用户要求补充 Mac 稳定性优化，安装 0.3.6 并完成下述有限实机验收。Windows 0.4.8 未安装，本轮该平台证据仍为源码局部运行。

## 已修复的缺陷

| 路径 | 原因及影响 | 修复 |
|---|---|---|
| Mac 连续本地 Seek | 旧文件校验晚返回后直接进入 prepare，先取消新控制器再发现自己失效，导致最新拖动失败 | 文件校验后复核实例/代次；prepare 在取消任何控制器前先检查调用者有效性 |
| Mac 回退时换曲 | quiesce/音量恢复等待结束后，旧事务仍可释放输出门、Load 旧曲并裁掉新曲资源 | 每个等待后复核实例/代次；失效事务不再修改全局资源与时钟 |
| Windows 回退时操作/换曲 | Seek/transport 队列直到异步准备和音量恢复后才创建；操作可能抛错或丢失，新曲还可能被旧事务的清理影响 | 第一处 await 前创建队列并保留期间操作；音量恢复后复核事务；旧实例进入 recover 时不清理新实例任务 |
| Windows 暂停后恢复 | 有界 PCM 可能淘汰暂停位置；Play 直接 start，缺口会触发欠载回退 | 先取得当前位置足够的有效 PCM 再启动，等待中保留最新暂停/Seek；恢复请求不伪造 Seek 通知，真实失败按最新播放意图回原生 |
| 两端下一首输出故障 | 共用流式时钟只发布 stream-failed，没有指明曲目；下一首故障也恢复正在正常播放的当前曲 | 错误携带曲目所有者；取消对应候选，当前曲错误仍走原生回退 |

未修改授权音源、档位选择、FLAC 转换、采样率、固定音量的线性增益、歌词/频谱数据格式、样式或缓存文件写入方式。无缝优先的原生音效策略沿用 0.3.5 / 0.4.7。

## Mac 稳定性及延迟优化

- 仅保留一首符合身份和格式的上一首资源，最多 128 MiB，仍计入原有总预算。有索引路径每首 PCM 32 MiB；编码共享 64 MiB。内存不足先释放这份暖缓冲，再对相同音源重试一次；不扩大预算、不建永久缓存。关闭、回退、清缓存及账号/档位变化释放。
- 原生源起播、Seek、恢复等目标位置需有连续两秒 PCM（曲尾按剩余时长），与 Windows 原有门槛对齐；其他流式路径保留 0.5 秒。减少刚取得目标首帧便出声、紧接着缺数据的风险；代价是冷目标可能多等一些取数。下一首提前预约，没有固定增加两秒曲间等待。
- 真实 Seek 取数失败按用户目标及最新播放意图恢复原生；主动取消、被替代、旧实例不会发起回退。复用的原生输出门更新持有者，旧 watchdog 不释放新曲的输出门。
- 输出上下文不可用时的 Play 由有序原生恢复事务接收，明确携带播放意图；不提前将 Play 发给仍停放的旧原生实例。实际分支隔离运行确认请求完成且恢复意图为 true。
- 共用 GainNode 将用户音量变更平滑到 5 ms，重复同值不重置自动化；输出门依然是预约时刻的精确阶跃。不加歌曲淡入淡出。即时增益跳变可能产生点击声，平滑参数符合 [GainNode 文档](https://developer.mozilla.org/en-US/docs/Web/API/GainNode) 和 [Web Audio 参数自动化标准](https://www.w3.org/TR/webaudio-1.0/#AudioParam)。
- Mac 系统 Seek 从接到请求到实际完成均暂停插件的进度发布，结束只更新最新位置；不改变真实播放状态。不是控制中心所有外观回跳的解决声明。
- Mac 辅助 Stop 后清缓存：已知索引观察最多两秒、至少等待 500 ms，需 250 ms 无变化；读取失败仍至少等 500 ms 再转交原生清理。只读索引，不把文件长度或稳定签名当作有效音频区间证明。
- 分开记录 source/buffer/context/gate/load 时间与预计输出时刻。后者用 getOutputTimestamp 映射到墙钟；只记录首次出声，不把后续暂停时长算成起播延迟。诊断时间戳不可读只记录缺失，不触发音乐回退。

## 局部运行证据

使用 Node 18.20.8，读取 HEAD 与工作树中的实际控制函数/回调，在隔离环境中安排延迟及新操作，比较执行结果。以下是受控协议/函数运行，不是实机声音证据；没有添加仓库测试用例。

- Mac stale prepare：修复前取消了新控制器；修复后返回 stale，新控制器未取消。
- Mac quiesce 期间换曲：修复前旧事务各执行一次 unmute、Load、retain；修复后均为零。
- Windows gain 等待期间换曲：修复前旧事务各执行一次 stop、close、cancelCandidate；修复后均为零。控制队列在 await 前已可用。
- Windows 有界 PCM 暂停恢复：修复前 start 时目标不可读；修复后 start 时已可读。准备期间暂停后没有 start，两个命令均完成，未发布合成 Seek。
- 两端错误归属：候选故障修复前都触发一次当前曲恢复；修复后只取消候选，当前曲恢复次数为零。当前曲自身故障修复前后都触发恢复。
- 最终修改的八个 JavaScript 文件增量语法和 git diff 空白检查通过；未执行全量 lint/TypeScript、应用构建或新增测试用例。
- 使用当前源码的类在真实 Mac CEF OfflineAudioContext 隔离渲染：固定单位增益 1920 个样本完全相同；1→0.5 在 5 ms 后为 0.5；20 ms 输出门在对应样本仍精确置零。只证明这些包络/静态增益，不替代真实音乐与原生设备对照。
- 实际 MacMediaSession 类的受控等待：Seek 期间强制 sync 两次，位置发布为零；完成后只发布目标 80 秒，pending 清除。模拟对象没有改动真实系统会话。
- 原生 getProperties 只读验证一份实际 IDX：两次签名一致、修改时间可读。NativeSource 实际方法隔离运行：稳定索引等约 513 ms，读取失败仍等约 501 ms，清理计时器无残留。未再次删除用户歌曲缓存，不宣称验证了原子提交。

## 保留的限制与待验收项

- 同采样率、下一首已准备且调度及时才可连续预约；不同采样率重建输出，允许间隔。流式输出仍需主线程及时补充预约，严重主线程阻塞或弱网会欠载，不能承诺所有场景零卡顿。
- Mac 控制中心进度回跳在纯原生也已观察；原生与 Chromium 两个状态发布者仍可能造成外观回跳/按钮闪动。没有将这个系统问题列为本轮已修复。
- Windows SMTC 历史宿主未提供时间线/Seek，物理媒体键、锁屏及最新候选跨曲更新仍需独立实机验收；不能用 Mac 证据代替。
- 两端清缓存均有有界稳定观察；Mac 的失败分支保留至少 500 ms 等待。Windows 失败分支对应改进见修复方案，尚未额外实施。均没有原生原子 flush 确认，不能排除观察窗口外的延迟提交。
- 未验证版本、格式、授权或设备路径仍回原生；本地文件大小/修改时间未变化的内容替换仍无法完全识别。
- 音量变化点击声风险已通过短平滑减少；原生音量曲线/曲目增益和最终设备输出仍未完成等响度对照。既有 PCM 数值证据成立，不能宣布原生/Web 最终输出逐位一致，也没有音质严重下降的证据。
- Windows 需按[修复方案](WINDOWS_REPAIR_PLAN_0.4.8.md)在其宿主验收后安装。Mac 未新增真实断网、不同设备、清缓存或所有格式的复测；原生回退竞态为实际函数隔离证据，不能替代每种故障的实机结果。

两端共用连续输出、解码和临时缓存职责，主要能力已有对应实现；系统控制与缓存清理时序存在明确差异。[既有功能矩阵](PLATFORM_ALIGNMENT_0.4.6_0.3.3.md)，[音质证据](AUDIO_FIDELITY_0.3.4.md)，[无缝优先策略](GAPLESS_PRIORITY_0.3.5.md)。
